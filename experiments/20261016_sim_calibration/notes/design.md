## 4. 較正の模型 jf-calib-v1

入力は、今のブリッジ・RL の先生が出している単位のままです。

- 舵 u_s [rad]: ±0.52 = PWM の端。
- 速さ u_v [m/s]: 負の値はブレーキ・後退の要求(ブリッジの換算: −(thr − 1498)/502 × 0.8)。

**舵と横**

1. 遅れ: u_s を d_s 秒遅らせる。小区間(≤ 10 ms)ごとに、指令の履歴から引く。
2. 対応: δ_target = g_L(u_s/0.52)(左)、g_R(|u_s|/0.52)(右)。区分線形で単調。節は正規化した指令の 0・0.25・0.5・0.75・0.9・1.0。値は δ = atan(L κ0)(κ0 = 低速での曲率、L = 0.26)。
3. 舵の速さ: δ は δ_target へ r_s rad/s で近づく。
4. アンダーステア: κ = tan δ / L / (1 + K_us v²)。
5. 横の限界: r = v κ を μ_s g / |v| で頭打ち。今の sim-core と同じ形で、路面 ID ごとの μ の値だけ替える。

**前後**

6. 遅れ: u_v を d_v 秒遅らせる。
7. 速さの対応: v_tgt = k_batt × T(u_v)。T は区分線形で単調。u_db 以下は 0(ESC の不感帯)。
8. 駆動(v_tgt > v): a = min(a_cap, μg, (v_tgt − v)/τ_up) − k_s |a_lat|。
9. 惰性(0 ≤ v_tgt ≤ v): a = −min(c0 + k_s|a_lat|, (v − v_tgt)/τ_down + k_s|a_lat|)。v_tgt より下へは行かない。前進側の指令では、ESC はブレーキを掛けない。
10. ブレーキ(u_v < 0、v > 0.05): a = −(c0 + k_s|a_lat| + a_b(off))。off = −u_v × 627.5 µs、a_b = s_b × max(0, off − db_b)。
11. ESC の後退: 止まったあとにブレーキ側の指令が来ても、後退しない。中立を 0.12 秒以上はさむと後退する(−0.8 m/s、1.5 m/s²)。
12. 電池: k_batt の既定は 1.0。感度を見るときは 0.8。

**入れないもの**: 摩擦円(縦と横の結びつきは、こすれ k_s だけ)、車輪の空転、ToF の雑音、画像、PCA9685 の周期(平均 8 ms。d_s・d_v に含める)。

**プロファイルは設定(config)に入れません。** 較正版のコアに焼き込み、`report().model.calibration` に名前と sha256 を残します。
`snapshot().config` は元と同じ形なので、先生やシールドは今までどおりの設定を見ます。

比べる 3 つの物理は次のとおりです。

- **P_default**: 今の評価・記録の物理。
- **P_cfg**: 今の設定欄だけで合わせた物理。動かすのは driveTau・driveAccelerationCap・brakeDeceleration(惰性とブレーキの共通)・steerRate・maxSteer(左右共通の頭打ち)・frictionMultiplier・アプリの遅れ 0〜2 フレーム。
- **P_cal**: jf-calib-v1。

| I9 k_batt | 電池 | シーンごとの効き g | 既定 1.0。忠実度では、窓の前 5 秒の g で合わせる | 1.0 |

- そのあと `profiles/P_cal.json`・`P_cfg.json` を書き、sha256 を記録してから、保留のシーンを 1 回だけ評価する。

## 6. 忠実度の物差しと合格の決まり

**再生**

- 較正版のコア(JS)を Node で動かす。dt = 0.01 秒、障害物の無い広い世界。
- 窓とその前 0.5 秒の、実際の指令(100 Hz)を流す。
- 始めの状態
  - v は実際の速さ。
  - δ は、前の 0.5 秒をその物理で流して得る。遅れのための過去の指令も、実際の値を入れる。
  - 向き・位置は 0。
- 路面は区間で決める(R1 → ショートカット、GM → 芝、ほか → カーペット)。
- 当てはめに使う Python の再生は、JS と 50 窓で一致すること(差 ≤ 1e-6)。

**指標**(保留のシーン、1 秒の窓、0.5 秒ずらし)

| 記号 | 意味 |
|---|---|
| e_v | 1 秒後の速さの誤差 [m/s](RMSE・中央値 = 偏り・p90) |
| e_r | 窓の中のヨーレートの誤差の RMS [rad/s] |
| e_ψ | 1 秒後の向きの誤差 [度](RMSE・中央値) |
| e_p | 1 秒後の位置の誤差 [m](RMS)。閉ループで「車がどこにいるか」にいちばん近い |

- まとめ方: 全体、操作者別、区間別(R1・GM・DE・LH・HS・SW)、速さの帯別。90% 区間はシーン単位のブートストラップで出す。
- 改善率は I = 1 − M(P)/M(P_default)。

**合格の決まり**

| | 決まり |
|---|---|
| C1 全体 | 4 つの指標すべてで I ≥ 0.20、かつ I の 90% 区間の下端 > 0。人・AI それぞれでも、e_v・e_r・e_ψ の I ≥ 0.10 |
| C2 区間 | R1・GM・DE・LH(窓 25 個以上)で、4 つの指標すべてが P_default の 1.05 倍以下。さらに R1 と GM で、e_ψ の I ≥ 0.10 |
| C3 偏り | e_v の中央値が ±0.10 m/s 以内(全体と R1・GM・DE)。e_ψ の中央値が ±2.0 度以内(全体)、±3.0 度以内(R1・GM・DE) |

- 判定
  - **合格** = C1・C2・C3 がすべて成り立つ。
  - **条件つき** = 全体で C1 が 4 指標のうち 3 つ以上で成り立ち、C2 の「悪くならない」と C3 の全体も成り立つ。
  - **不合格** = それ以外。
- 参考に出すもの
  - 安定性: 保留のシーンで当て直したパラメーターが、25% 超ずれたら印を付ける。
  - 2 秒の窓の同じ表。
  - P_cfg の判定。
  - 電池を合わせない P_cal(k_batt = 1)の表。
- 目安: 10/16 の下調べでは、遅れと舵の速さを変えるだけで、ヨーの誤差が 21% 減った。τ を変えると、1 秒先の速さの誤差は 16% 減った。対応表・こすれ・惰性を足せば、20% は届く見込み。
- 成果の決め方
  - P_cfg が合格なら、画面の設定欄で入れられる P_cfg を第一に勧める。
  - 上限の試験の物理は、P_cal が合格か条件つきなら P_cal。不合格なら P_default と P_cal の両方で走らせ、結果は「仮説」と書く。

## 7. ユーザーのファイルを変えずに当てる方法

| やり方 | できること | 判断 |
|---|---|---|
| 画面の設定欄・アプリの config(driveTau・brakeDeceleration・steerRate・maxSteer・摩擦の倍率・遅れのフレーム) | 式はそのまま。惰性とブレーキの区別・左右の頭打ち・純粋な遅れ・こすれ・速さの頭打ちは表せない | **P_cfg として比べる**(合格ならこれを勧める) |
| RL の環境の物理の乱し(env_core の perturb) | 上と同じ 5 つの値 + 遅れ 0/1 フレーム + ゲイン。Node の RL の環境の中だけ | 使わない |
| JetFormer の画面(jetformer/sim/web.py の import map の差し替え) | ブラウザでいつでも使える | jetformer/sim の変更と jetformer-web の再起動が要る。**製品にするときの道**として報告に書くだけ(ユーザーの了承が要る) |
| **読み込むときに差分を当てた較正版のコア** | 全部の効きを入れられる。Node とブラウザで同じ実装 | **これを使う** |

**較正版のコアの作り方**

- `calib_runtime.mjs`: 較正の物理と上限の層を書いた、純粋な ESM(import なし)。
- `calib_core.mjs` の `patchSimCore(元の文字列, プロファイル)`: 元の sha256(`aaeb2379…`)を確かめ、step の物理の部分などを 1 か所ずつ置き換える。
  置き換える場所が 1 か所でなければ止まる(10/13 の `fast-sim-core.mjs` と同じ書き方)。
- `calib_runtime` の中身は、文字列のままコアに埋め込む(data: URL の中からは相対の import ができないため)。
- Node: `loadCalibratedCore(プロファイル, {fast})` で data: URL から読む。fast を付けると、10/13 の高速化(近くの障害物だけ判定する。元と結果が同じことは確認済み)も重ねる。
- ブラウザ
  - 10/15 のシミュレーターの写しを、このフォルダーの `sim/` に写す。dist の全ファイルが元と sha256 で同じことを確かめる。
  - `dist/_calib/sim-core-<名前>.js`(静的なファイル)と、`dist/calib.html`・`dist/calib_cap.html` を足す。
  - index.html との差は、title と import map の 1 行(`"./sim-core.js": "./_calib/sim-core-<名前>.js"`)だけ。
  - app.js だけでなく、先生のモジュール(speed-controller.js など)も同じコアを読む。予測も同じ物理になる。

**試験**

| | 確かめること |
|---|---|
| T1 | プロファイル無しの較正版(fast あり・なし)が、元と同じ。教師の REC60(60 条件)・STD・ランダム操作 20 本で、report の JSON が完全に一致する |
| T2 | 元の sha256 が違う、または差分の場所が 1 か所でない → 止まる |
| T3 | Python の再生と JS が一致する |
| T4 | ブラウザ用のファイルが、差分の関数の出力とバイト列で同じ。ページの差が import map と title だけ |
| T5 | 新しい物理の部品(惰性・ブレーキ・後退の手順・遅れ・頭打ち・アンダーステア・電池)を、手計算の値で確かめる |
| T6 | 上限の層の不変条件。Python の安全層 v1 の関数が既にあれば、2,000 通り以上の入力で同じ判断になること |

## 8. 速度上限の試験(シミュレーター)

**上限の層 governor_v1_sim**(計画項目 9 と fast_and_safe_plan.md N1 の仕様をシミュレーターに写したもの)

- 置き場所: 較正版のコアの step の始め。アプリの遅れのあとの指令に掛ける。
  - 見る状態は step の始めのもの。実車の層が見る eRPM の新しさと、1 フレーム以内で同じ。
  - Node とブラウザで同じ実装を使う。
- 区間(位置で決める、主の方法)。車の位置を参照ループ R に射影した s で決める。

| 区間 | R の s [m] | 上限 | ブレーキ |
|---|---|---|---|
| R1_app(LH の後半 〜 R1 の始まり。実車の「ψ ≥ 300」に当たる) | 5.02〜6.21 | 2.5 m/s | 出す(条件つき) |
| R1_turn(R1 の始まり + 約 0.5 秒) | 6.21〜7.46 | 2.5 m/s | 出さない |
| GM | 8.24〜12.60 | 2.2 m/s | 出さない |
| DE(GM 出口 + 約 1.5 秒) | 12.63〜16.15 | 3.0 m/s | 出さない |

- 区間(ジャイロで決める、副の方法): 実車と同じジャイロの位相(explore_control.md C1)で、シミュレーターのヨーから作る。
  - 最初の R1 の前と、位相が不確かなときは、全区間 3.0 m/s。
  - Python の安全層 v1 があれば、その移植にする。
- 決まり
  - v ≤ 上限: 速さの指令を上限で切る。
  - v > 上限: 中立(惰性)。
  - v > 上限 + 0.3 m/s、v ≥ 1 m/s、かつ R1_app のとき: ブレーキ(中立 + 200 µs = −0.319 m/s の指令)。
  - ブレーキは 0.2 秒は保つ。やめたら 0.2 秒は再開しない。
  - 区間を出たら、上限を 1.5 m/s² で戻す。
  - 舵は変えない。指令を大きくはしない。
- 不変条件(上限ありのすべての走行で 0)
  - R1_turn・GM・DE でのブレーキ。
  - 1 m/s 未満でのブレーキの始まり。
  - 0.2 秒未満のブレーキ ↔ 中立の往復。
  - 指令を大きくしたフレーム。
  - 後退。
- 変えた版: R1 だけ 2.75 m/s(計画どおり再生で比べる値)。

**運転手**

| 運転手 | 何か | 役目 |
|---|---|---|
| **PP-k**(k = 1.0・1.2・1.4) | 新しく作る追従の運転手(Node)。経路はコース図の基準線(33 ゲート・ショートカット・すき間を確かめ、だめなら参照ループ R)。純追従で舵を切り、指令は使う物理の舵の対応の逆にする。速さは曲率と μ から決める(限界の 85%)。旋回の速さに k を掛け、後ろ向きの計算は惰性だけ(ブレーキなし)。上限は 4.3 m/s | **主**。較正した物理を知っている運転手で、実車のデータで学んだモデル B の代わり。k = 1.2・1.4 は R1 などに速く入りすぎる運転手(first_trial の速い進入に当たる) |
| RL の先生 fastest・speed(c_v = 0.75) | mode_runtime.mjs をそのまま使う。シールドなし。指令の速さは 0 以上(ブレーキを出せない) | **主(頑健さ)**。古い物理で学んだ、物理を知らない運転手 |

**条件**

- 主の組み合わせは 10 条件 × 24 開始。
  - 運転手: PP-1.0・PP-1.2・PP-1.4・RL-fastest・RL-speed-0.75。
  - 上限: なし・あり(位置の区間、R1 2.5)。
  - 物理は P_cal(ブレーキは名目)、世界は v3。
  - 1 走行は 60 秒の連続周回で、最初の衝突で終わる。アプリの遅れは 1 フレーム。
  - 開始は Halton で選んだ 24 個(ゲート・左右 ±0.15 m・向き ±10 度。すき間 < 0.12 m の開始は替える)。
- 副の条件
  - R1 2.75 m/s(5 運転手)。
  - ブレーキの弱め・強め(PP-1.2・PP-1.4・RL-fastest)。
  - **P_default でも上限なし・ありを走らせる**(較正で結論が変わるか)。
  - 芝の斜めの板を足した世界 W+(PP-1.2・RL-fastest)。
  - ジャイロの区間(PP-1.2・RL-fastest)。

**指標**

- 区間の通過ごとに、次を記録する。
  - R1 の進入の速さ: R1 の始まりの手前 0.4 秒の最大。実車の entry_erpm と同じ定義。
  - GM の始まりの速さ。
  - DE の中の最高速度。
  - 衝突。
- 率
  - 区間ごと: R1・GM・DE の衝突 / 通過。
  - 全体: 衝突 / 走った周(距離 ÷ 26.12 m)。
  - 衝突の無い周の時間。
  - 上限の層の作動の割合とブレーキのフレーム。
- 90% 区間は、開始単位のブートストラップで出す。

**決め方**

| 決まり | 内容 |
|---|---|
| 判定に使えるか | 上限なしで R1 の通過が 30 回以上、かつ R1 に 2.5 m/s を超えて入った割合が 20% 以上 |
| R1 に効いた | R1 の衝突/通過が相対で 50% 以上減り、差の 90% 区間の上端 < 0 |
| ほかで悪くならない | 全体の衝突/周の差の 90% 区間の上端が +0.05 以下 |
| ラップの損 | PP-1.0・PP-1.2 で、同じ開始どうしの差の中央値が +0.3 秒/周以下(実車のゲート G4 と同じ) |
| 不変条件 | すべて 0 |

- 判定
  - **シミュレーターで支持**: PP-1.2 と PP-1.4 で R1 に効き、全運転手でほかが悪くならず、ラップの損と不変条件を満たす。
  - **支持(条件つき)**: 片方だけ効く、またはブレーキの弱めで崩れる。
  - **効く場面なし**: 判定に使える運転手が無い。
  - **直す**: ほかが悪くなる、または不変条件が破れる。
- 2.75 m/s が 2.5 m/s の効きの 80% 以上を、小さい損で出せれば、「2.75 も候補」と書く。決めるのはユーザー。
- ブレーキの弱めで効きが崩れるなら、「ブレーキ表の実測(計画項目 8)が前提」と書く。

**シミュレーターと実車の突き合わせ**(閉ループでの較正の確かめ)

- 上限なしの走行で、R1 の衝突の確率を進入の速さのロジスティック回帰で表し、確率 20% の速さ v20 を出す。P_cal と P_default の両方で出す。
- 実車の値: AI は 2.75 m/s 未満で 1/21、2.75〜3.1 で 2/7、3.1 以上で 6/8。人は 2.75 未満で 1/53、3.1 以上で 5/12。20% を超えるのは 2.75〜3.1 m/s。
- **v20(P_cal) が 2.4〜3.3 m/s なら「R1 の物理は実車と矛盾しない」。**
- ただし失敗の形が違う。シミュレーターは内側の柱への切り込み、実車の強い衝突は外側の白い板への曲がり切れなさ。衝突した相手の物も並べて出す。

## 10. 分からないこと・限界

- **実機のデータは 10/10 の 1 日だけ。** 電池の電圧の記録が無く、効きの変化は推定です。
- **速さは eRPM から出しているので、滑ると大きく出ます**(芝・強い加速)。横の限界は IMU の横加速度で出します。
- **ブレーキは 16 回(強いもの 3 回)だけです。** 上限の試験のブレーキは、幅を持たせて走らせます。
- **運転手の問題があります。** 画像で走る実機のモデル(B)は、シミュレーターでは走れません(evidence_simulator.md 0 章 2)。
  - PP と RL は、モデル B の代わりです。分かるのは「上限という画像を使わない層が、この物理でどう効くか」です。モデル B の衝突の数は予測しません。
- **コース図は推定です。** 芝の斜めの板の有無と、DE の斜めの赤い板は、実車で確かめます(計画項目 1)。
- **AI の PWM の対応が人と違えば、その理由の確かめは実車の日に回します**(PCA9685 の発振の確認)。
- 結果は実車の A/B/A の代わりではありません。実車に入れるかは、G1(記録の再生)と、ユーザーの了承のあとです。
