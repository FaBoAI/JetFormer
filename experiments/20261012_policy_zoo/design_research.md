### 0.2 今日わかったこと(数字は CPU の計算)

1. **TCP 型のラベルは今のデータから作れる。** IMU のヨー(z、正 = 左)と eRPM の速さ(v = −eRPM × 0.5e-3)を積分すると、
   1秒の窓が取れるのは学習に使うフレームの 93〜96%。符号の確認は3通りとも合った(§4.3)。
2. **ステア → 曲率の較正は、左右で同じ傾き・左右で違う頭打ち・速度で小さくなる。** 遅れ 40 ms で当てはめると
   0.0039(左)/ 0.0040(右)/m/µs(R² 0.81)。頭打ちは低速で 左 1.37・右 1.70 /m、3 m/s 以上では左右とも 0.9〜1.0 /m。
   tof_guard の `K_LEFT = 0.00275` は小さい切れ角では小さすぎる(頭打ちの値から決めたとみられる)。
3. **コース図との突き合わせ**: ヘアピン(LH・R1・GM)の基準線の曲率は 1.43 /m(半径 0.70 m)。データの「右いっぱいに切ったときの曲率」が
   1.43 を下回るのは約 2.7 m/s より上。これは右ヘアピン R1 の進入の上限 2.75 m/s(5500 eRPM。`explore_control.md` C2)と合う。
   左いっぱいは 2〜3 m/s ですでに約 1.2 /m なので、左ヘアピン(LH・GM)は基準線より外を回っているか、もっと遅い(芝の GM は低μでさらに小さい)。
4. **完全な予測をしても、制御器を通すと人の操作との差は消えない(§4.6)。** 正解の未来の道から作ったステアは 34 µs(3フレーム先)で
   モデル B(48.7 µs)より小さい。一方、正解の未来の速さから作ったスロットルは 51.7 µs で、モデル B(44.9 µs)より **大きい**。
   さらに、短い先読みで通過点を追うと、通過点の 5 cm の横ずれがステアで約 180 µs の誤差になる。
   → **TCP 型の良さ(速度の上限・つまみ)は、検証の L1 では見えない。L1 の比較では TCP 型は不利になるのが当然**で、
   R1・DE の進入と速度の指標で判断する。既定の組み合わせは「ステアは学習した操作、速度は目標速度 + 制御器」にする。
5. **DINOv2 ViT-S/14 は、最小の実装(約120行)で公式の重みが過不足なく読めた**(`strict=True`、21.63M)。車の画像 16枚で、
   注意のロジットの最大は 384(通常版)/ 177(レジスタ版)、残差の最大は 20 / 102 で、FP16 の上限 65504 より十分小さい
   (DINOv3 では 2.1×10⁶ になり FP16 が NaN になった報告がある)。ONNX(opset 17)にも書き出せた(525ノード)。TensorRT の確認は GPU が要る。
6. **予測の重ね合わせ(temporal ensembling)は、方策に依存しない走行側の選択肢にする**(既定オフ)。ACT は「古い予測ほど重く」(m = 0.01)だが、
   私たちは「新しい予測ほど重く」(m = 0.5、重ねるのは3つまで)を勧める(前の解析で揺れ −25〜−40%、遅れ 0 フレーム)。
7. **期待は控えめにする。** モデル B は学習 15 µs・検証 49 µs で強く過学習している。TransFuser の論文でも融合の段数の差は乱数の種の
   ばらつきの中(1段 49.35、既定 49.49〜56.68)、TF++ の「経路+速度」と「通過点」も検証では誤差の中(50±3 対 49±8)。
   **学習ごとのばらつき(約10 µs)を超える L1 の差は、どの方策でも出ない可能性が高い。** 「どれがベストか」は §7 の手順を先に決めて判断する。

## 2. 走行側の共通の選択肢: 予測の重ね合わせ(temporal ensembling)

### 2.1 元の研究(ACT)

- ACT は毎ステップ問い合わせ、同じ時刻を指す古い予測と新しい予測を平均する。重みは `w_i = exp(−m·i)`、**i = 0 が一番古い予測**で、
  公式の実装は m = 0.01、重みは合計 1 に正規化する(`imitate_episodes.py` の `k = 0.01`)[ACT-code]。チャンクは 100 ステップ(50 Hz で 2 秒)なので、
  最大 100 個の予測を、ほぼ同じ重みで平均している。
- 論文の効果: ACT で +3.3 ポイント(チャンクの大きさの効果 1% → 44% に比べると小さい)[ACT]。
- チャンクを開ループで実行すると、予期しない状態への反応が遅れる(一貫性と反応の速さの引き換え)という指摘がある [BID]。

### 2.2 私たちの車への置き換え

- 予測は 10 ステップ(0.33 秒)で、先読み la(既定 3)の予測を使う。時刻 t + la を指す予測は `pred_{t−j}[la−1+j]`(j = 0..10−la)。
- 式: `e_t = Σ_{j=0..J} w_j · pred_{t−j}[la−1+j] / Σ w_j`、`w_j = exp(−m·j)`(**j = 0 が一番新しい**)。既定 **J = 0(オフ)**、使うときは J = 3・m = 0.5。
  - 前の解析(`experiments/20261011_day_summary/explore_control.md` C9・A5)で、006/007/010 の再生では、J = 3・m = 0.5 でステアの1フレームの変化が −25〜−40%、
    遅れ 0 フレーム。ACT と逆向きの重み(新しいほど重い)にするのは、壁が急に見えたときの反応を遅らせないため。
- 置き場所: `drive.py` で `pred`(µs、[10,2]、数値の確認の後・先読みの前)に掛ける。**すべての方策に同じ関数**(numpy、torch なし。
  例 `jetformer/policies/ensemble.py`)を使い、評価の道具(順に予測する `compare_models.predict_scene` など)も同じ関数を呼ぶ。
  `tcp` では制御器の出力([10,2])に掛ける。
- 規則: 前の予測が中立で止めた行(hold)・フレームの間隔が (j + 0.5) × 50 ms を超える・先読みが違う、のどれかなら、そこで打ち切る。
  記録には生の予測と重ねた後の値の両方を残す。今の操作値を入れるモデル(`command_input`)の `vehicle_state` には生の予測を戻す(学習と同じ条件)。
- 走行のパラメータ: `ensemble_j`(0〜3、既定 0)・`ensemble_m`(0〜2、既定 0.5)。`/api/drive/params` で変えられ、走行の開始の body は変わらない。
- リスク: 急な変化への反応が鈍る(J ≤ 3 に制限)。衝突/周・ラップへの効果の証拠はまだない(前の解析の結論のまま)。比較(§7)では **オフ** で比べ、
  別の行として「オンにしたときの揺れ」を出す。

## 3. `act` — ACT 型(行動のステップごとの問い合わせを持つ Transformer の Decoder)

### 3.1 元の研究(Zhao ほか, RSS 2023)[ACT][ACT-code][LeRobot-ACT]

- 構造: CVAE。方策(デコーダ側)は ResNet-18 の特徴(カメラ4台、各 15×20×512 → 300 トークン、2次元の正弦波の位置)+ 関節位置 + z を
  Transformer Encoder(4層)に入れ、**k 個の学習できるクエリ**(DETR と同じ `query_embed`)が Decoder で Encoder の出力を参照し、
  k × 14 の目標関節位置を出す。d = 512、8 ヘッド、FFN 3200、dropout 0.1、約 80M パラメータ。
- Decoder は論文では 7 層だが、公式コードの不具合で **1層目しか使われていない**(LeRobot は合わせて `n_decoder_layers = 1`)[LeRobot-ACT]。
- CVAE の符号化器: [CLS] + 関節位置 + 行動の列(画像は入れない)→ 4層 → CLS から μ・logσ²(32次元)。推論では z = 0(事前分布の平均)。
- 損失: L1(L2 より精密とある。数値の比較はない)+ β·KL、β = 10。Adam lr 1e-5、バッチ 8。1課題 50 デモ(10〜20 分)、2080 Ti で約5時間。
- 効いたもの(論文の図7): チャンクの大きさ k = 1 → 100 で成功率 1% → 44%(4つの設定の平均)。重ね合わせ +3.3%。
  CVAE を外すと、スクリプトのデータではほぼ同じ、**人のデータでは 35.3% → 2%**。

### 3.2 私たちの車への置き換え

```
image ─ResNet-18→ 49 ┐
tof  ─ToFEncoder→ 42 │ (v0 と同じトークン化・同じ位置/種類の埋め込み)
imu/state/genre → 3  ├→ Encoder 4層(d256, 8ヘッド, FFN 512, pre-norm)→ memory [B,95(+1),256]
(z トークン 1: CVAE のときだけ)┘
query_embed [10,256] ─→ Decoder 2層(自己注意 + memory への交差注意, d256, 8ヘッド, FFN 512)→ [B,10,256]
                         → LayerNorm → heads: Linear(256, num_modes×2)(10個のクエリで共有)→ ジャンルを one-hot で選ぶ → [B,10,2]
```

| 項目 | 既定 | 理由 |
|---|---|---|
| トークン | v0 と同じ(画像 49・ToF 42・IMU・操作値・ジャンル)。v0 の「出力用トークン」は無し | v0 との違いを Decoder だけにする |
| Encoder | 4層・d256・8ヘッド・FFN 512 | v0 の融合と同じ大きさ(v0 の重みからの部分的な初期値も使える。段階3) |
| Decoder | **2層**(選択肢 1〜4)。クエリ 10個(1 クエリ = 1 フレーム先) | 元の実装は実質1層。2層で「クエリどうしの調整」と「場所ごとの参照」が両方入る |
| ヘッド | `heads = Linear(256, num_modes·2)` をクエリで共有。`mode_embed` は v0 と同じ | `--init-mode-copy` 用に `genre_keys = {embed: mode_embed.weight, heads: heads, rows_per_mode: 2}` |
| CVAE | **既定オフ**。オンなら [CLS] + ジャンル + 10個の行動トークン(Linear(2,256)、正弦波の位置)→ 2層 → 32次元。z → Linear(32,256) で Encoder の1トークン。推論は z = 0(書き出したグラフには符号化器が入らない) | 1人の運転・33 ms × 10 ステップの短い列では、多峰性は小さいと見込む。比べるなら β ∈ {1, 10} |
| 損失 | L1(v0 と同じ)+ CVAE のとき β·KL(KL は 32次元の和、バッチの平均。ACT と同じ) | 検証の µs は L1 のまま |
| 凍結 | なし(v0 と同じく ResNet-18 も学習) | — |
| 書き出し | `nn.TransformerDecoder`(batch_first、norm_first)。`mha` の fastpath は切る(今の書き出しと同じ) | 固定の形・opset 17 で通る(`bench/` の試作で書き出し済み: 14.78M、647 ノード) |

- 大きさ: 約 15.7M(v0 14.08M − 出力トークン/trunk + Decoder 2層 1.58M)。CVAE の符号化器 1.05M は学習のときだけ。
- 推論: Decoder の 10 クエリは軽い(10 × 95 の交差注意)。v0 + 0.1〜0.5 ms と推定(カーネルの数が増える分)。
- 学習の速さ・メモリ: v0 とほぼ同じ(1エポック 約35 秒、ピーク 約3 GB と推定)。

### 3.3 学習・評価の注意

- ACT の学習率(1e-5、バッチ 8)は使わない。比べるために v0 と同じ(3e-4、64)。
- CVAE を試すときは、KL が 0 に張り付いていないか(z が使われていない = 普通の ACT と同じ)を `result.json` に残す(`kl` の最後のエポックの値)。
- ACT の本体の効果(チャンク)は、v0 がすでに持っている(10 ステップを一度に出す)。私たちは毎フレーム問い合わせ、la の1ステップだけを使う
  (チャンクを開ループで実行しない)。30 fps の車では反応の遅れのほうが怖いので、開ループの実行は勧めない [BID]。

### 3.4 何がうまくいかないか

- **伸びしろが小さい**: v0 との違いは「1つの出力トークン → 20 個の数」か「10 個のクエリ → 各 2 個」かだけ。期待できるのは遠いステップ(k10。モデル B のステアは
  k1 42.7 → k10 56.1 µs)の改善くらいで、L1 の差は乱数の種のばらつき(約10 µs)の中に入る可能性が高い。
- 約6千サンプルで Decoder を足すと過学習が増える(モデル B ですでに学習 15・検証 49 µs)。dropout 0.1 のまま、エポックは 30 で同じにする。
- クエリが「平均的な列」に寄る(L1 は中央値に寄る)。CVAE はそれを防ぐ手だが、z = 0 での推論は「一番ありそうな型」を出すだけで、多峰性の利点は走行では限られる。

## 4. `tcp` — TCP / TransFuser++ 型(通過点 + 目標速度 → 制御器、速度に上限をかけやすい)

### 4.1 TCP(Wu ほか, NeurIPS 2022)[TCP][TCP-code]

- 入力: 前方カメラ 900×256(FOV 100°)を ImageNet の ResNet-34 で、速さ・目標地点・ナビの指令を MLP で。
- **軌道の枝**: 画像の特徴を平均して計測の特徴とつなぎ、GRU で K = 4 個の通過点(2 Hz、2 秒先)を1つずつ出す。
  通過点の間のベクトルの長さ = 目標の速さ → 縦の PID(Kp 5.0・Ki 0.5・Kd 1.0)、向き → 横の PID(Kp 0.75・Ki 0.75・Kd 0.3)。
- **操作の枝**: 多ステップの操作(K = 4)を、GRU の時間のモジュールと「軌道に導かれた注意」(軌道の枝の隠れ状態から、各未来ステップで画像のどこを見るかの注意の地図を作る)で出す。
  操作はベータ分布で表し、教師(Roach、強化学習のエキスパート)の分布との KL で学習する。特徴の損失(教師の潜在に寄せる)・速さと価値の補助の頭もある。
- 損失の重み: λ_traj = 1・λ_ctl = 1・λ_F = 0.05・λ_aux = 0.05(速さと価値の回帰は 0.001)。Adam 1e-4、バッチ 128、60 エポック。データ 189K(ablation)/ 420K サンプル(2 Hz)。
- **状況で混ぜる**: 過去 1 秒のステアの絶対値の半分以上が 0.1 を超えたら「曲がっている = 操作の枝が得意」、それ以外は「軌道の枝が得意」。
  得意な枝に 1 − α、もう一方に α(α = 0.3)。リーダーボードでは非対称(軌道が得意なら α = 0.5、操作が得意なら α = 0)、ブレーキは大きいほう。
- 結果(CARLA): 操作だけ 32.45±2.23・軌道だけ 28.29±3.03(DS)。軌道だけは曲がるときの違反が多く(「単純な PID の追従が悪い」)、操作だけは車への衝突が多い。
  部品の積み上げ: 軌道を補助タスクに +2.5、時間のモジュール +7.9、軌道に導かれた注意 +3.2、混ぜる(α = 0.3)で DS 57。

### 4.2 TransFuser++(Jaeger・Chitta・Geiger, ICCV 2023)[TF++][carla_garage]

- **経路**(1 m おきの 10 点、速さに依存しない)と **目標速度**(4 クラス: 0・7・18・29 km/h)に分ける。通過点は止まっているときにステアの手がかりが無くなる、が理由。
- 目標速度は、クラスの頻度で重みをつけた交差エントロピー。推論では **確からしさで重みをつけた平均**(argmax にすると車への衝突が 0.83 → 1.25 /km に増える)。
  確からしさのしきい値で全ブレーキにする規則もある(しきい値 25〜50% で DS 58〜61、差は小さい)。
- 横の制御: 車の中心から「狙いの距離」(5.5 m/s 未満で 2.25 m、以上で 3.0 m)より先の最初の点を PID で追う。
- 経路と速度のクエリを持つ Transformer の Decoder(6層・8ヘッド)→ GRU → 累積和。
- 結果は控えめに読む: 検証では「通過点」49±8 と「経路 + 重みつき平均」50±3 で差は誤差の中。リーダーボードでは通過点版 62・経路版 53 で、
  著者も 9 ポイントの差を説明できていない。データの拡張(±1 m・±5°)で 43 → 49、背骨を凍結すると 54 → 44。3つの種で学習し、標準偏差は ±1〜±9 DS。

### 4.3 ラベルの作り方(clean_driving_20261011 で確かめた)

元データ: `can_bus/<scene>_ms_imu.json`(約100 Hz、`rotation_rate[2]` rad/s)と `can_bus/<scene>_vehicle_monitor.json`(約100 Hz、`erpm`)。

1. ジャイロのバイアス b: ログごとに、止まっている間(|eRPM| < 1 かつ |gz| < 5°/s)の gz の中央値(50 サンプル未満なら 0)。今のデータで −0.0016 rad/s。
2. 速さ v(t) = −eRPM(t) × 0.5e-3 [m/s](IMU の時刻へ線形補間。後退は負)。
3. IMU の時刻で積分: ψ = ∫(gz − b)dt、X = ∫ v cos ψ dt、Y = ∫ v sin ψ dt(dt は 0〜50 ms に切る)。速さの方向を向きとするので、点は後輪の軸の中心に近い。
4. フレーム i(時刻 t₀)の自車座標(**x = 前、y = 左**、単位 m)へ:
   `x_k = cos ψ₀·ΔX + sin ψ₀·ΔY`、`y_k = −sin ψ₀·ΔX + cos ψ₀·ΔY`(ΔX = X(t₀ + 0.1k) − X(t₀) など、k = 1..10)。
5. 目標速度: **v_tgt = t₀ + 0.2〜0.5 秒の v の平均**(制御器の時定数 0.33 秒に合わせ、eRPM の揺れをならす)。分布(学習、t₀ + 0.33 秒の v):
   p5 0.0・p10 1.42・p25 1.93・p50 2.49・p75 3.22・p90 3.75・p95 4.02・p99 4.46 m/s。
6. 有効の印 `wp_valid`: 1秒の窓がシーンの中、窓の中の IMU の切れ目 < 50 ms、窓の中で後退しない(v ≥ −0.1)、衝突の前後でない(今の 2.5G の除外と同じ)。
   無効のフレームは通過点と速度の損失だけ外し、操作の枝(`actions` の L1)は今までどおり学習する。

精度の目安: ジャイロの倍率の誤差は 1〜2%(コース図の当てはめ g = 1.008〜1.021)→ 1 秒で 120° 回るときの向きの誤差 約2°。
eRPM の速さは空転で ±6% → 1 秒(約2.5 m)で ±0.15 m。1秒先の横の位置の広がり(\|y\| の中央値 1.1 m)に比べて小さい。
芝(GM)では空転で v が大きく出て、曲率 ω/v が小さく出る(`explore_control.md` の 0.74〜0.85 倍の一部はこれかもしれない)。
コース図(`experiments/20261011_overnight/course/`)との照合: `tracks_*.json` は AI 走行のログ(006/007/009/010/101)で、clean_driving の人のシーンは入っていないので、
軌跡どうしの照合はしていない。代わりに基準線の曲率(ヘアピン 1.43 /m)と、データの「いっぱいに切った曲率」の速さの関係が R1 の上限と合うことを確かめた(§0.2 の3)。
コース図の当てはめ(`tools/course_fit.py`)も同じジャイロと距離の積分なので、独立した確かめにはならない。独立に近い確かめとしては、生ログの hall のカウント(5 mm/カウント)の距離と
eRPM の積分の距離を 1秒の窓で比べ、空転の分(特に GM)を見積もることを勧める。

実装: 学習の前に1回、シーンごとに計算して `data/datasets/<ds>/derived/tcp_labels_v1.npz`(scene・frame・waypoints [N,10,2]・v_tgt [N]・wp_valid [N]・
作り方の版)にキャッシュする(CPU で 1 分以内)。データセットは「追加の正解」を **最後の dict**(`interfaces.md` §5.6 の追加の入力と同じ仕組み、キーは `y_` で始める)で返す。
評価の道具も同じ npz を読む。

### 4.4 モデル

```
v0 と同じトークン → Encoder 4層(d256)→ memory
queries: 通過点 10・速度 1・操作 10(学習できる埋め込み)→ Decoder 2層(クエリどうしの自己注意 + memory への交差注意)
  通過点クエリ → heads_wp: Linear(256, num_modes×2) → Δ(x, y) → 累積和 → waypoints [B,10,2](m)
  速度クエリ   → heads_v : Linear(256, num_modes×10) → speed_logits [B,10](0, 0.5, ..., 4.5 m/s)
  操作クエリ   → heads   : Linear(256, num_modes×2) → actions [B,10,2](正規化。v0 と同じ意味)
```

- TCP の「軌道に導かれた注意」は、**同じ Decoder の自己注意で操作のクエリが通過点のクエリを参照できる** 形に簡単にする(GRU は使わない。
  TensorRT でループを避ける)。`act` と同じ Decoder のコードを使い回せる。
- 速度は **10 クラスの two-hot**(隣り合う2クラスに線形で分ける。例 2.3 m/s → 2.0 に 0.4・2.5 に 0.6)で学習し、推論は期待値 Σ pᵢ vᵢ。
  TF++ の「確からしさで重みをつけた平均」と同じ考えで、クラスの中心のずれが無い。分類にする根拠は TF++ のほか、回帰を分類に直すと安定する報告 [StopRegressing]・two-hot [DreamerV3]。
- 損失: `L = 1.0·L1(actions) + 0.5·L1(waypoints [m]) + 0.1·CE_twohot(speed)`(通過点と速度は `wp_valid` のときだけ)。重みは最初に決めて固定し、
  検証で調整しない(検証は 11 シーンしかない)。TCP の特徴の損失・価値の頭は、教師が人なので使わない。今の速さの補助の頭も、eRPM が入力にあるので使わない。
- 書き出し: `actions`・`waypoints`・`speed_logits` の3つ(`EXPORT_OUTPUTS`)。`actions` は **操作の枝**なので、今の走行・評価の道具はそのまま動く
  (`tcp` を知らない走行でも、操作の枝で走れる = ACT 型と同じ)。大きさ 約15.8M(`bench/` の試作は GRU 版で 14.23M)。

### 4.5 制御器(どこで動かすか、と中身)

**決定: 制御器は ONNX の外、Python(numpy だけ)で動かす。** 置き場所は `jetformer/policies/controller.py`(torch を読まない)。

| 理由 | 内容 |
|---|---|
| 走行中の速度の上限 | 上限・速さの倍率・混ぜ方は走行のパラメータで、エンジンを作り直さずに変えたい。グラフの中に入れると入力を足すことになる(`FEED_KINDS` が増える) |
| 同じコードで評価 | 走行(`drive.py`)と評価の道具(`compare_models`・`rl_evaluate predict`・新しい比較の道具)が **同じ関数** を呼ぶ。torch とnumpy の二重実装を作らない |
| 較正の差し替え | ステア → 曲率の表・スロットルの写像は車の性質で、電池やタイヤで変わる。学習の後に CPU で当てはめ、`model_config.json` の `postprocess` 欄に書く。作り直すのは表だけ |
| 互換 | `actions` は操作の枝として ONNX に残るので、H2 の約束(`actions [1,10,2]`)は崩れない。`trt_runtime` はすべての出力をホストへ写すので、追加の出力も読める |

`model_config.json` に `postprocess: {"kind": "tcp_controller", "version": 1, ...較正の値...}` を足す。`drive.model_info` は kind を知らなければ
「操作の枝だけで走れる」として扱う(安全側)。

**1フレームの処理**(入力: `waypoints [10,2]`・`speed_logits [10]`・`actions [10,2]`・今の速さ v_now(state と同じ eRPM)・走行のパラメータ):

1. 目標速度 `v_hat = Σ softmax(logits)·bins` → `v_cmd = min(speed_scale × v_hat, speed_cap)`(上限 0 = なし)。
   上限を外したときの突き上げを防ぐため、`v_cmd` の増え方を 1.5 m/s² に制限する(`explore_control.md` C2 と同じ)。
2. **ステア**(10ステップ、k = 1..10、時刻 k/30 秒): 予測の通過点を 0.1 秒刻みの道とみなし、その時刻の位置と向き(隣の点の差)に自車を置いて、
   残りの道の上で弧長 `L = max(L_min, T_la × v)` の点を pure pursuit で追う: κ = 2y_L / (x_L² + y_L²)[PurePursuit]。
   κ → µs は **速度帯ごとの表**(§4.6 の較正。頭打ちも表に入る)で逆引き。道の長さが 0.2 m 未満(止まっている)なら操作の枝のステアを使う。
3. **スロットル**(10ステップ): 前向きの写像 `thr = c0 + c1·v_now + c2·(v_cmd − v_now)/0.33`(今のデータで c0 1530・c1 −82.7 µs/(m/s)・c2 −25.4 µs/(m/s²)。`tcp_label_check.json` の `throttle_feedforward`、検証の誤差 51.6 µs)。
   - `v_cmd < 0.3` なら中立。通常は **中立より上(ブレーキ・後退側)を出さない**(写像の切片 1530 は中立 1496 より上なので、切らないと止まりぎわに後退の手順に入りうる)。
   - ブレーキ: `v_now − v_cmd > 0.3` かつ `v_now > 1.0 m/s` のときだけ中立 + 150 µs(C7 の規則。ESC は前進 → 後退 = ブレーキ、後退は R → N → R)。
   - 積分の項は **既定で使わない**(ログの速さは私たちの指令に反応しないので、開ループの評価で積分が飽和し、走行と評価が食い違う)。実車のシャドーの後で検討する。
4. **混ぜ方**(`tcp_mode`):
   - 0 = **hybrid(既定)**: ステアは操作の枝、スロットルは 3 の速度の制御器(v_cmd に上限と倍率が入る)。速さの「つまみ」が使えるのはこの形と 2。
   - 1 = fusion: TCP と同じ状況で混ぜる(過去 1 秒の |ステア − 中心| > 100 µs が半分以上なら操作の枝に 0.7、そうでなければ軌道に 0.7)。
   - 2 = trajectory: ステアもスロットルも制御器(2 と 3 だけ。TF++ に近い)。
   - 3 = control: 操作の枝だけ。上限を入れたときだけ、スロットルを「操作の枝」と「3 の写像で v_cmd = 上限 としたもの」の **前進の少ないほう** にする
     (上限で前進を弱めるだけで、速くはしない。実車で最初に試すなら一番控えめな形)。
   - どの形でも、最後に「上限の写像より前進を強くしない」を掛ける(hybrid・trajectory では元から満たす)。
5. 出力 [10,2] µs → ここから先は今までと同じ(予測の重ね合わせ → 先読み → ゲイン → ToF ガード → 補助/リカバリー → 書き込み)。
   **安全の仕組みはどれも変わらない。** ゲインは操作の後に掛かるので、`tcp` では速度ゲイン 1.0 を勧め、速さは `speed_scale`・`speed_cap` で変える。

hybrid を既定にする理由: §4.6 のとおり、通過点からステアを作ると予測の誤差が大きく増える一方、速度の上限・つまみは「目標速度 + eRPM の閉ループ」でしか作れない
(速度ゲインはモデルに打ち消される。`explore_learning.md` §0)。TCP 自身も「曲がるときは操作の枝が得意」と報告している。

**曲率から決まる速度の上限(任意、既定は表示だけ)**: 予測した道の最大の |κ| から、表の「いっぱいに切った曲率」κ_full(v) が `1.1 × |κ|` を下回らない最大の v を
`v_curv` として表示する(例: 右ヘアピンの 1.43 /m なら、余裕 1.0 で約 2.7 m/s、余裕 1.1 で約 2.1 m/s。今の表は速度帯が3つで粗いので目安)。
有効にすると `v_cmd = min(v_cmd, v_curv)`。

**較正の当てはめ**(`tools/fit_controller.py`、CPU、学習の最後に `train.py` から呼ぶ。`--resume` で作り直せる):
学習のシーンだけで、(a) 遅れ 0〜250 ms でステア(t)と κ(t + 遅れ) = ω/v の当てはまりが最も良い遅れ、(b) 速度帯(〜2・2〜3・3 m/s〜)× ステアのずれ 50 µs 刻みの
曲率の中央値の表(単調にそろえる)、(c) スロットルの前向きの写像、(d) pure pursuit の `T_la`・`L_min` を **予測した通過点で**(正解ではなく)検証の L1 が最小になる値
(格子: T_la 0.15〜0.5 秒、L_min 0.2〜0.6 m)。結果は `model_config.json` の `postprocess` に書き、走行と評価はそれだけを読む。

**走行タブ**: 方策が `tcp` のときだけ、予測の目標速度 v_hat・上限後の v_cmd・今の速さ・(任意)v_curv を表示し、`speed_cap`(0 = なし、0.5〜5.0 m/s)・
`speed_scale`(0.5〜1.5)・`tcp_mode`(0〜3)のスライダーを出す。パラメータは `PARAM_LIMITS` に数値で足す(開始の body は変わらないので `DRIVE_CLIENT_VERSION` は 6 のまま)。
記録(`AI_CMD`)に v_hat・v_cmd・どの枝が出力を決めたかを残す(`explore_control.md` C10 の「どの層が決めたか」のシャドー)。

### 4.6 制御器の誤差の下限(今日の計算。`tcp_label_check.json` の `oracle_controller`)

「未来の実際の道(正解の 1 秒の通過点)と未来の実際の速さを、制御器に入れたら、人の操作 `future_actions` とどれだけ違うか」を、検証の stride 3 のフレーム
(1秒の窓が取れる 1502 フレーム)で計算した。モデルの誤差ではなく、**制御器と較正だけで生じる誤差**。

| 作り方 | ステア k1 / k3 / k10 [µs] | スロットル k1 / k3 / k10 [µs] |
|---|---|---|
| 正解の道 + pure pursuit(L = max(0.2 m, 0.15 s × v))+ 速度帯の表 | **34.2 / 34.4 / 34.8** | — |
| 同じ、先読みを長く(0.35 s × v) | 46.9 / 47.5 / 47.1 | — |
| 同じ、直線の較正(左右同じ傾き、頭打ちなし) | 37.1 / 37.4 / 38.2 | — |
| 未来の実際の曲率をそのまま逆引き(遅れ 40 ms) | 36.5 / 37.4 / 37.8 | — |
| 未来の実際の速さ → 前向きの写像 | — | **50.3 / 51.7 / 51.4** |
| 参考: モデル B(compare.json、きれいな検証フレーム、自己入力 = 教師入力) | 42.7 / 48.7 / 56.1 | 41.5 / 44.9 / 50.7 |

(フレームの集合はモデル B の行と同じではない。目安として読む。)

読み方:

1. **ステア**: 道が完全に分かれば、制御器のステアはモデル B より小さくなりうる(k10 で 35 対 56 µs)。人は「近い道」に合わせて切っている(先読み 0.15 秒が最良)。
2. **ただし通過点の誤差が増幅される**: pure pursuit の κ = 2y/L² なので、L = 0.375 m(2.5 m/s × 0.15 s)で通過点の横のずれ 5 cm は κ で 0.71 /m、ステアで約 180 µs になる。
   L = 0.9 m(0.35 s)でも 0.12 /m ≈ 31 µs。予測した通過点で使うには先読みを長くするしかなく、そのとき下限は 約47 µs(モデル B の k3 と同じ)まで上がる。
   → **ステアを通過点から作っても、L1 ではモデル B に勝ちにくい**。だから既定(hybrid)ではステアは操作の枝にする。
3. **スロットル**: 未来の速さが完全に分かっても、人のスロットルとの差は 51.7 µs で、モデル B の 44.9 µs より大きい。人のスロットルには、速さだけでは説明できない
   動き(ブレーキ、ためらい、電池の電圧)がある。→ **速度制御のスロットルは L1 では必ず不利に見える**。速度の制御の良さは、速さの誤差(m/s)と R1 の進入の速さで測る。
4. ステア → 曲率の較正(`steer_to_curvature`): 遅れ 40 ms で R² 0.81(0 ms で 0.69、120 ms で 0.63)。小さい切れ角の傾きは左 0.00393・右 0.00401 /m/µs で **左右ほぼ同じ**。
   速度で小さくなる(1〜2 m/s: 0.0051/0.0046、2〜3: 0.0044/0.0040、3〜5: 0.0033/0.0032 → アンダーステア)。いっぱいに切ったときは 右 −1.65〜−1.70・左 +1.34〜+1.37 /m。
   tof_guard の `K_LEFT = 0.00275`・`K_RIGHT = 0.0039` は、右は合うが左は小さい切れ角で約3割小さい(頭打ち 1.3 /m ÷ 約470 µs から決めた値とみられる)。
   ToF ガードの「指令の円弧」にも効くので、別に直す候補(この作業では変えない)。

### 4.7 何がうまくいかないか

- **L1 で良さが見えない**(§4.6)。比較では、操作の枝の L1(v0 と同じ定義)・制御器の出力の L1(混ぜ方ごと)・通過点の誤差(ADE/FDE、m)・目標速度の誤差(m/s)を
  別々に出し、判断は R1・DE と速度の指標(§7)で行う。
- **速度の上限とモデルの干渉**: 上限で抑えると eRPM が下がり、モデル(state に eRPM がある)は目標速度を上げ続ける。上限を外したときの突き上げは、v_cmd の増え方の制限で抑える。
- **開ループの評価の限界**: ログの車は私たちの指令に反応しないので、上限の効き目(R1 に何 m/s で入るか)は机上では「指令がどれだけ前進を弱めたか」しか分からない。
  効き目そのものは実車(シャドー → A/B)でしか分からない(この作業では走らせない)。
- **較正の変化**: 芝・PTFE(低μ)では曲率が 0.74〜0.85 倍、電池の電圧でスロットル ↔ 速度が変わる。区間で違う較正は C1(区間の判定)ができてから。
- **止まっている・後退**: 止まっているとき通過点は 0 に縮み、ステアの手がかりが無い(TF++ が経路に分けた理由)。→ 道が 0.2 m 未満なら操作の枝のステア。後退はラベルから外し、補助/リカバリーに任せる。
- **ブレーキと後退の手順**: 写像の切片が中立より上なので、切らないと止まりぎわに中立より上を出し、ESC が後退の手順に入りうる。§4.5 の規則(中立より上は 1 m/s 以上のブレーキだけ)を必ず入れる。
- **ラベルの符号の取り違え**: 自車座標(x 前・y 左)、ヨー正 = 左、ステア大 = 左、前進 = µs 小。CPU のテストで「左ヘアピンのフレームで y > 0、κ > 0、ステア > 中心」を確かめる(§8)。
- **ジャイロの飽和**: 衝突で ±1000 dps に張り付く。衝突の前後は除外済みだが、2.5G 未満の接触で飽和した窓が残りうる → |gz| > 15 rad/s を含む窓は無効にする。

## 5. `msfusion` — 本家 TransFuser に近い多段融合

### 5.1 元の研究(Prakash・Chitta・Geiger CVPR 2021、Chitta ほか IEEE TPAMI、arXiv 2022)[TransFuser][TransFuser-PAMI][TransFuser-code]

- 画像(3台をつないだ 704×160、RegNetY-3.2GF、ImageNet)と LiDAR の鳥瞰図(256×256、0.125 m、高さ2段 + 目標の印。同じ背骨を最初から学習)。
- **4つの解像度で融合**: 各段の特徴を平均プーリングで最終段の格子(画像 5×22 = 110、LiDAR 8×8 = 64 トークン)に縮め、学習できる位置の埋め込みを足し、
  1段に1つの Transformer(論文: 4層・4ヘッド、埋め込みの次元 = その段のチャネル数 72/216/576/1512。2022 年版のコードの設定は `n_layer = 8`)を通し、
  出力を **双線形で元の解像度へ拡大して各枝の特徴に足す**。最後に両枝を平均プーリング → 512 次元 → **要素ごとの和** → MLP → GRU で通過点 4 個。
- 補助タスク: 深度(L1)・セマンティクス(7クラス)・鳥瞰の地図(3クラス)・車両の検出(CenterNet)。コードの重みは通過点 1.0・地図 1.0・深度 1.0・セマンティクス 1.0・検出 各0.2。
- ablation(Longest6、DS): 補助タスクなし 44.29 対 既定 49.49〜56.68(**種の最悪〜最良**)。融合の段数 1: 49.35・2: 53.52・3: 48.77・4(既定)。注意の層 2: 53.49・6: 56.24・8: 56.13
  (「2〜8 層で似た性能」)。片方向だけの融合 46〜48。遅い融合(LF)22.47 対 TransFuser 47.30(アンサンブル)。RTX 3090 で LF 23.5 ms・TransFuser 27.6 ms。
- 読み方: **一番効いているのは補助タスクと「融合すること自体」(遅い融合との差)で、段数の差は種のばらつき(約7 DS)の中**。JetFormer v0 は「最終段のトークンで1回融合」で、
  TransFuser の言う遅い融合(特徴ベクトルの足し算)より強い形(49 + 42 トークンの注意)になっている。

### 5.2 私たちの車への置き換え

| 段 | 画像(ResNet-18、ImageNet) | ToF(新しい CNN) | 融合の Transformer(既定) |
|---|---|---|---|
| 入力 | 3×224×224 | 距離・信頼度・有効の印 3×42×54 → **上下 3 行・左右 1 列の 0 で詰めて 48×56**(詰めた所は無効 = 0) | — |
| 1 | layer1 64×56×56 → 平均(8×8 窓)→ 7×7 | 32 → 64ch 24×28 → 平均(4×4)→ 6×7 | d64・4ヘッド・2層・FFN×4 |
| 2 | layer2 128×28×28 → 平均(4×4)→ 7×7 | 128ch 12×14 → 平均(2×2)→ 6×7 | d128・4ヘッド・2層・FFN×4 |
| 3 | layer3 256×14×14 → 平均(2×2)→ 7×7 | 256ch 6×7 | d256・4ヘッド・2層・FFN×4 |
| 4 | layer4 512×7×7 | 256ch 6×7(stride 1)→ 1×1 で 512ch | d512・4ヘッド・**1層・FFN×2**(重いので) |
| 後 | 最終段のトークン(画像 49・ToF 42、各 1×1 で 256)+ IMU・操作値・ジャンル・出力用トークン → **v0 型の融合 2層**(d256)→ 出力トークン → trunk → ジャンル別ヘッド [10,2] | | |

- 各段: 画像 49 + ToF 42 = 91 トークン(段ごとに学習できる位置と種類の埋め込み)→ Transformer → 分けて元の格子に戻し、**双線形で拡大して各枝の特徴に足す**(TransFuser と同じ)。
- 格子は全部割り切れる大きさにする(ToF を 48×56 に詰めるのはこのため)。torch の `AdaptiveAvgPool2d` は割り切れないと ONNX に出せないので、固定の `AvgPool2d` と `F.pad` だけを使う。
- 最後を TransFuser の「平均プーリング + 和 + MLP」ではなく **トークンの融合**にする理由: v0 の一番強い部分(最終段の 91 トークンの注意)を残し、`msfusion` を
  「v0 + 早い段の交換」にして、比べたときの違いを融合の段だけにする。TF++ でも、平均プーリングを Transformer の Decoder に替えると近道の害が減った [TF++]。
  選択肢 `head: pooled` で TransFuser どおりの形も作れるようにする。
- 補助タスク: **既定なし**。選択肢 `aux_depth`: 画像の枝の最終段から ToF の距離(42×54、信頼度 4 以上だけ、L1、重み 0.1)を当てる小さな頭(学習のときだけ)。
  カメラと ToF の画角の対応が分からない(ToF の光線モデル 1.2°/列が仕様と合わない疑い、`explore_learning.md`)ので、画素の対応は使わず、全体の特徴から格子を出す形にする。
  TransFuser で一番効いたのは補助タスクなので、時間があれば2本目の比較として入れる。
- 凍結: なし(ResNet-18 も学習)。ToF の CNN は BatchNorm(v0 と同じ)。
- 大きさ: 画像 11.2M + ToF 約1.3M + 交換の Transformer 約4.2M(0.10 + 0.40 + 1.58 + 2.10)+ 後の融合 約1.1M + ヘッドなど ≈ **約18〜19M**
  (`bench/` の試作は 19.4〜22.2M)。
- 推論: ResNet-18 1.8 GMACs + 交換 約0.4 GMACs + 後の融合 0.1 + ToF 0.2 ≈ 2.5 GMACs → **3〜4 ms と推定**(拡大・足し戻しのカーネルが増える)。
- 学習のメモリ: ResNet-18 の活性はそのまま、交換は小さい → v0 の 1.1〜1.3 倍(約3.5 GB と推定)。`hints.min_free_mb` 4000。

### 5.3 何がうまくいかないか

- **過学習**: パラメータが v0 の 1.3 倍。学習のデータは同じ約6千サンプル。TransFuser の段数の ablation が種のばらつきの中だったことから、L1 の差は出ない見込みが高い。
- **ToF は LiDAR の鳥瞰図ではない**: TransFuser の LiDAR は上から見た格子で、カメラとは視点が違うから「注意で対応をつける」意味が大きい。私たちの ToF はカメラとほぼ同じ向きの
  距離画像(5 cm 以内)なので、交換で新しく分かることは少ないかもしれない。ToF を自車座標の鳥瞰の格子にする案(`explore_learning.md` M4 の2)は、
  光線モデルの較正が先なので、この方策では使わない。
- **早い段の ToF が弱い**: 42×54 の入力から 4段を作ると、早い段の ToF の特徴はほとんど生の距離。早い段の交換は画像 → ToF の方向に偏る(TransFuser の注意の解析でも早い段の LiDAR → 画像はほぼ 0)。
- **FP16**: 交換の段の d512 は残差の値が大きくなりやすい。TRT と PyTorch(FP32)の差 ≤ 0.005(2.5 µs)を合格の条件にする(今の v0 は最大 0.0007)。
- **推論が重い**: カーネルの数が v0 の約2倍(ONNX 951〜1619 ノード、v0 488)。4 ms を超えたら第4段の交換を外す(選択肢 `scales: [1,2,3]`)。

## 6. `dinov2` — DINOv2 の画像特徴

### 6.1 元の研究と、運転・ロボットでの使われ方

- DINOv2(Oquab ほか 2023)[DINOv2]: ラベルなしの自己蒸留で 1.42 億枚の厳選した画像から学習した ViT。**凍結のままの特徴**で分類・分割・深度に強い。
  ViT-S/14(蒸留): 21M、ImageNet k-NN 79.0%・線形 81.1%(レジスタ付き 79.1%・80.9%)。**コードと重みは Apache-2.0** [DINOv2-code]。
- 公式の hub の作り方 [DINOv2-code]: `img_size = 518`(位置埋め込みは 37×37)、`patch_size = 14`、LayerScale あり、通常版は補間 `antialias = False`・`interpolate_offset = 0.1`、
  レジスタ版(4個)は `antialias = True`・`offset = 0.0`。重みは `https://dl.fbaipublicfiles.com/dinov2/dinov2_vits14/dinov2_vits14_pretrain.pth`(88,283,115 バイト)、
  レジスタ版 `dinov2_vits14_reg4_pretrain.pth`(88,291,785 バイト)。
- レジスタ(Darcet ほか ICLR 2024)[Registers]: 大きなモデルでは、背景の一部のパッチに高いノルムの「人工物」が出て、特徴の地図が汚れる。レジスタのトークンを足すと消える。
- 運転・ロボット:
  - CARLA で、DINO の自己蒸留で事前学習した画像の符号化器は、分類の事前学習より効率が良かった [DINO-driving]。
  - ロボットの把持で、分布のずれ(照明・模様・邪魔な物)への強さは、ViT の「自然に出る分割の能力」でよく予測でき、ImageNet の正解率では予測できなかった [Burns2023]。
    私たちのカメラは、1日の中で取り付けの角度がずれた(バンパーの写る行が 6〜8 → 9〜10)。凍結した汎用の特徴は、こうしたずれに強い可能性がある(**仮説**)。
  - 事前学習した特徴を壊さないには、まず頭だけ学習(線形プローブ)し、その後に全体を小さい学習率で微調整する(LP-FT)のが良い [LP-FT]。
  - 逆の結果もある: TF++ では背骨を凍結すると DS 54 → 44 に落ちた(ただし ImageNet と知覚の事前学習の背骨)[TF++]。
- Orin Nano での速さ(文献、TRT 10.3・JetPack 6.2・MAXN_SUPER、GPU の時間だけ)[OrinNano-latency]: ViT-S/16(224 px)FP16 **2.36 ms**、FP32 で作り直すと 5.92 ms。
  その論文の課題では、すべて FP16 のエンジンで正解率が 4〜7 ポイント落ちた(FP32 で戻った)。DINOv3 ViT-S/16 では FP16 で注意のロジットが 2.1×10⁶ になり、
  出力が全部 NaN になった報告がある(BF16 なら 0.9996 の一致)[kornia-DINOv3]。

### 6.2 私たちの車への置き換え

```

  → ViT-S/14(凍結、eval)→ 正規化した 256 パッチ [B,16,16,384] + CLS [B,384]
  → パッチ: Linear(384→256)→ 2×2 の平均で 8×8 = 64 トークン、CLS: Linear(384→256)で 1 トークン
tof/imu/state/genre → v0 と同じ(ToF 42、各1)
  → [64 + 1 + 42 + 3 + 出力用 1 = 111 トークン] + 位置・種類の埋め込み → 融合 4層(d256, v0 と同じ)→ 出力トークン → trunk → ジャンル別ヘッド [10,2]
```

| 項目 | 既定 | 選択肢・理由 |
|---|---|---|
| 背骨 | `dinov2_vits14`(通常版)。重み `data/pretrained/dinov2_vits14_pretrain.pth`(すでに置いてある、09:26 に別の作業で取得) | `variant: vits14_reg4`(レジスタ版。今日の確認で人工物のパッチ 0%、§6.3) |
| 実装 | **リポジトリの中の最小の ViT**(`jetformer/policies/vit.py`、約120行、キーは公式と同じ)。torch.hub・xformers に依存しない | `dinov2_cpu_check.py` の `ViTS14` がそのまま下敷きになる |
| 位置埋め込み | 読み込みのときに 1回だけ 37×37 → 16×16 へ双三次で補間(hub と同じ設定)して **パラメータとして持つ**。`best.pth` に入るので、走行・評価で補間しない | ONNX に補間の演算が入らない |
| トークンの数 | 2×2 の平均で 64(+ CLS)。融合は 111 トークン(v0 は 95) | `pool: 1` で 256 トークン(融合が約3倍重い) |
| 凍結 | **全部凍結**(`requires_grad = False`、eval)。学習するのは 約2.9M | `finetune_last: 2` で最後の2ブロックと最後の LayerNorm を学習率 0.1 倍(3e-5)。`param_groups` のフック(`interfaces.md` H14)が要る。LP-FT の順(凍結で学習した `best.pth` から `--init`)を勧める |
| 色の揺らぎ | 今のまま(RGB のゲイン 0.8〜1.2) | 凍結でも揺らぎはそのまま使える(特徴をキャッシュしないため) |
| 注意の実装 | 明示的な `(q·scale) @ kᵀ → softmax → @ v`(ONNX で MatMul + Softmax) | `F.scaled_dot_product_attention` でもよいが、書き出しの形を確かめること |
| エンジン | FP16。`model_config.json` の `engine` 欄で BF16 / FP32 にも切り替えられるようにする(`interfaces.md` H10) | Orin(Ampere)は BF16 が使える見込み。TRT 10.16 で要確認 |

- 大きさ: ViT 21.63M(凍結)+ 射影 0.2M + ToF 0.39M + 融合 2.11M + MLP・ヘッド ≈ **24.5M**(学習するのは約2.9M。`bench/` の試作と同じ)。`best.pth` は約98 MB(FP32)。
- 推論: ViT-S/14 は 257 トークン × 12 層で 約6.1 GMACs(ViT-S/16 の 4.6 GMACs の約1.3倍)。文献の 2.36 ms から **ViT 約3 ms + 融合 約0.5 ms + ToF ほか → 3.5〜5 ms と推定**。
  JetPack 7.2・TRT 10.16 での実測は `bench/` に任せる。
- 学習: ViT の順伝播は勾配なし(活性を保存しない)なので、メモリは v0 より小さい見込み(約2 GB)。計算は ResNet-18 の約3倍の順伝播 → 1エポック 40〜70 秒と推定。

| 高いノルムの「人工物」パッチ(中央値の4倍超) | 0.12% | 0% |
| ONNX(opset 17・`dynamo=False`) | 525 ノード(MatMul 72・LayerNormalization 25・Softmax 12・Erf 12 ほか)、出力 [1,257,384] | 544 ノード、出力 [1,261,384] |

→ DINOv3 の報告(ロジット 2.1×10⁶)のような FP16 のあふれは、DINOv2 ViT-S/14 と私たちの画像では起きない見込み。ただし CPU の FP16 は TensorRT の融合カーネル(myelin)
と同じではない。**TRT の FP16 エンジンと PyTorch FP32 の差(`actions` で ≤ 0.005)を合格の条件にし、だめなら BF16 → FP32 の順に試す**。
(この確認は 09:39〜09:42 に 1スレッド・nice 19 で行った。同じ時間に `bench/` の GPU の計測が動いていたので、その CPU 側の時間にわずかに影響したかもしれない。)

### 6.4 何がうまくいかないか

- **凍結した特徴が運転に必要な細部を持たない**: 14 px のパッチで、床のテープ・レールの端などの細い物が粗くなる。2×2 の平均でさらに粗くなる → `pool: 1`(256 トークン)と比べる。
- **低い視点・屋内のコース**: DINOv2 の学習画像とはずれがある。凍結のままでは、v0(ResNet-18 を全部学習)に L1 で負ける可能性がある(TF++ の凍結の結果)。→ LP-FT の2段目(最後の2ブロック)を比較に入れる。
- **速さ**: 推定 3.5〜5 ms(v0 の約2倍)。カメラ → PWM 約28 ms に +2〜3 ms。FP16 が使えないと FP32 で 6 ms を超える見込み。
- **学習の時間**: ViT の順伝播が重い。凍結なら特徴をキャッシュして速くできるが、色の揺らぎと両立しない(既定はキャッシュしない)。
- **重みの取得**: 管理画面からの最初の学習のとき、`data/pretrained/` に無ければ止めて知らせる(`interfaces.md` H15)。ネットから自動では取らない(電源断の途中で壊れたファイルを残さないよう、取得は別の手順で `.part` → 名前の変更)。

### 7.1 学習の組み合わせ(GPU は1つずつ、`--resume` で再開できる順に)

| 段 | 学習 | 本数 | 時間の目安(1本) |

- 設定はモデル B と同じ(§1.3)。CLI から一括で回し(管理画面からは衝突のしきい値が 4.0G になる。`interfaces.md` §2.8)、各学習の `run.json` に種を残す。
- 合計 約6〜9 時間の GPU。1本終わるごとに評価(CPU で済む部分)を書き出し、終わったものは飛ばす。

### 7.2 指標(全部の方策で同じ道具・同じフレーム)

1. **検証の L1 [µs]**(`actions`、clean_driving の検証 11 シーン)。種ごとの値と平均。ステア・スロットル別、k1/k3/k10(`compare_models.py`)。符号の正解率・前進の偏り。
2. **R1・DE の保留の通過**(`rl_evaluate.py` の判定の関数 `heldout_passes`・`_pass_values`・`entry_estimate`・`cluster_bootstrap` を使い、各方策 − モデル B を通過ごとのブートストラップで。
   `evaluation.json`(ゲートC)は触らず、別のファイル `eval/zoo_<名前>.json`)。R1 の進入のスロットルと eRPM の見積もり、DE のステア、直線の前進の強さ。
3. `tcp` だけ: 混ぜ方ごと(control / hybrid / fusion / trajectory)の L1、通過点の ADE/FDE [m]、目標速度の誤差 [m/s]、上限 2.75 m/s のときの R1 の進入での指令の変化。
4. **ずれへの強さ**(新しい、方策に依存しない机上の試験): 検証の画像を 3 行下・上へずらす(取り付けの角度のずれ相当)、明るさ ×0.8・×1.2、ToF を 1 行ずらす、のそれぞれで L1 の増え方。
   `dinov2` の利点が出るとすればここ(仮説)。
5. 速さ・書き出し: TRT FP16 の平均と p99(`benchmark_model.py`)、TRT と PyTorch FP32 の差の最大、エンジンの大きさ、学習の最大メモリ、1エポックの時間。
6. 予測の重ね合わせ(J = 3)をしたときの揺れ(別の行。判定には使わない)。

### 7.3 判定の規則(結果を見る前に固定する)

- **合格の前提**: TRT FP16 の推論 ≤ 6 ms、TRT と FP32 の差 ≤ 0.005、学習のメモリが 8 GB(スワップなし)で安全(ピーク ≤ 4 GB)。満たさなければ走行の候補にしない。
- **モデル B より良い** と言えるのは、次のどれか:
  - 検証の L1 の種の平均が **10 µs 以上** 小さく、種の範囲が重ならない。
  - L1 が同じ程度(±10 µs)で、R1 または DE の指標の差のブートストラップの 90% 区間が 0 をまたがず、良い向き。ほかの指標(前進の偏り・直線の前進の強さ)が悪くならない。
  - `tcp` は L1 を条件にしない(§4.6 で不利と分かっている)。代わりに、操作の枝の L1 がモデル B と同じ程度(±10 µs)で、hybrid の速度の上限が R1 の進入の指令を下げ、直線の前進を下げないこと。
- どれも満たさなければ **「机上ではモデル B より良いと言えない」** と書き、走行はモデル B のまま。複数が満たすときは、速い・単純なほうを選ぶ。
- 机上の結果は実車の改善を示さない。最後は実車の A/B/A(この作業では走らせない)。

### 7.4 結果の見込み(先に書いておく。後で答え合わせをする)

| 方策 | L1 の見込み(モデル B 49 µs に対して) | ほかの見込み |
|---|---|---|
| `act` | ±5 µs(ばらつきの中) | k10 がわずかに良くなるかもしれない |
| `tcp` | 操作の枝 ±5 µs。trajectory は +10 µs 以上悪い | 速度の上限・つまみが手に入る(机上では効き目を測れない) |
| `msfusion` | ±10 µs(過学習の向きが心配) | 推論 約2倍 |
| `dinov2` | −10 〜 +15 µs(一番読めない) | ずれへの強さで差が出るかもしれない。推論 約2倍 |

## 9. 未解決・注意

- 推論の時間はすべて推定。`bench/` の TRT の実測で置き換える。
- `tcp` の効き目(速度の上限)は机上では測れない。机上で言えるのは「指令がどう変わるか」まで。
- tof_guard の `K_LEFT`(0.00275)は、小さい切れ角ではデータの傾き(0.0039)より約3割小さい。ToF ガードの「指令の円弧」に効く。この作業では変えない(別の課題)。
- 1秒先のラベルは、シーンの終わりの約1秒で作れない(シーンがつながっていないため)。生ログからシーンをつなげば取り戻せるが、今回は使わない。
- 管理画面からの学習は衝突のしきい値が 4.0G で、モデル B(2.5G)と比べられない(`interfaces.md` §2.8)。比較は CLI で行う。
- 解析の数字はこの日のデータ(clean_driving_20261011)だけのもの。速さと較正は電池・タイヤ・路面で変わる。
