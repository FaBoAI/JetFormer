## 1. 前提(確認済みの事実)

- コース v3 `indoor-course-eval-3-turf-board-removed`: 33 ゲート(`targets = route[1..32] + route[0]`、横 ±0.65 m、順番どおり)、
  黒シートの必須横断(z = 0 を −z 向きにまたぐときに車幅全体が x 1.26〜2.36 m の中、1 周に 1 回)、経路長 27.27 m。
- 物理(`real-drive-response-estimate-v1`): 加速 = min(6, μg, (目標 − v)/0.4)、減速はいつも 1.2 m/s²、ヨーレートは μg/|v| で頭打ち(滑りなし)。
  路面 μ: カーペット 0.8・黒シート 0.7・青マット 0.65・芝 0.6・PTFE 0.22。1 フレーム 1/30 s を 31 の小区間に分けて計算(maxSpeed 7.24 のとき)。
- 教師(RC 教師、正解の位置を使う): 連続 20 秒 × 60 シーンで 1 周目 8.7097〜8.7584 秒、2 周目 8.3589〜8.4068 秒、衝突 0。
  標準の開始は 1 周目 8.7584・2 周目 8.3701 秒。単周(停止から 1 周)8.9308 秒。指令の上限 4.5 m/s、最小すき間 6.1 cm。
  遅延 1 フレームでは 16 ゲート後に衝突、開始のずれ 0.2 m・12° 以上でも衝突する(余裕が小さい)。
- 学習済み ONNX `shortcut-rc-finetuned`: 停止から 8.964117 秒(モード 4・先読み 1・前進ゲイン 1.01・遅延 1)。遅延 0 では衝突。
- 実車(`clean_driving_20261011`、eRPM から): 走行中の速さの中央値 2.55、99% 点 4.4〜4.5、最大 約 5 m/s。速さ × ヨーレートの 95% 点 約 9 m/s²。
  操舵が端に張り付く時間 3.4%(教師 8.1%)。
- 記録: ヘッドレス Firefox では WebGL が動かない。DISPLAY :0 に窓を開くと WebGL 2(llvmpipe = CPU 描画)が動き、約 10 フレーム/秒。
  差し込み口を置き換えたページ `rl.html` で、アプリ自身の収集器・集約が元のまま使えることを 2 シーンで確認済み(PWM の再計算の差 0 µs)。
- PWM の換算: 元の 20 分データは 1442 / 1498 µs。収集器の既定は 1441 / 1496 µs なので、ブリッジに `calibration_only_policy.py` を付ける。
- JetFormer をシミュレーターのデータだけで学習すると、`model_config` の `steer_center_us`/`throttle_neutral_us` が 1375.3 / 1332.9 µs になる
  (止まっているフレームの中央値。各シーンの最初の 1 フレームしかない)。シミュレーターで走らせる前に 1442 / 1498 に直す必要がある。
- シミュレーターの推論アダプター(`jetformer_policy.py`)は num_modes 1〜9 だけを受け付ける。JetFormer の bundle には `simulator_*` の項目が無く、
  無いと画面は仮の校正(最高 1.6 m/s)で走らせ、ユーザーの検証器も通らない。onnxruntime は jetracer 環境にも他の venv にも無い
  (PyPI に aarch64・cp313 の wheel はある)。

## 2. RL の定式化

### 2.1 環境(Node、ヘッドレス、ベクトル化)
- 物理は `experiments/20261013_sim_rl_bestlap/sim/fast-sim-core.mjs`(元の `dist/sim-core.js` を読み込み時に 3 か所だけ置換。sha256 227ceccc…)と
  `sim/world-v3.json`(sha256 57de53a5…)。three.js を読まないワーカーで 1 つ 74 MB。
- ワーカー `rl/env_worker.mjs` を 4 つ起動し、それぞれ 16 環境を持つ(計 64)。Python の学習側は、全環境の行動を Float32 で各ワーカーの標準入力へ送り、
  観測・報酬・終了・打ち切りを Float32 で受け取る。エピソードの要約(周回時間・終わった理由・最小すき間など)は 1 行の JSON で別に返す。
  自動リセットはワーカー側で行う(終了した環境は次の観測としてリセット後の観測を返し、終了前の最後の観測も別に返して価値の補いに使う)。
- 特徴の計算は共有の ESM `rl/features.mjs` に置き、Node の環境とブラウザの差し込みモジュールの両方が同じファイルを import する。
- 開始(停止状態)は `probe` の `makeSim(k, off, turn)` と同じ方法(アプリの reset と同じ: 経路をゲート k で回し、左へ off [m]、向きを turn だけずらす)。
  開始位置が障害物と重なる(`invalid_spawn`)ときは引き直す。

### 2.2 物理の設定(20 分データと同じ。変えない)
`dt 1/30, maxSpeed 7.24, maxSteer 0.52, acceleration 1.2, steerRate 1.2, vehicleLength 0.42, vehicleWidth 0.19, wheelbase 0.26,
stopOnCollision true, frictionMultiplier 1, noiseStd 0, timeLimit 20, episodeMode continuous-laps-v1,
longitudinalModel real-drive-response-estimate-v1, driveTau 0.40, driveAccelerationCap 6, brakeDeceleration 1.2`。
制御遅延は 0(教師と同じ。記録のラベルの約束)。前進ゲインは掛けない(ゲイン 1.01 は外部 ONNX のアダプターの話)。

### 2.3 観測(79 次元。特権的な情報 = 正解の状態から計算)
参照ループ R = RC 教師の単周の参照軌跡(`createRcTrainingTeacher` の標準の開始の `reference.points`、1,092 点・26.12 m)を閉じたもの。
**座標の物差しと先読みの形にだけ使い、R に沿うことへの報酬は与えない**(方策は R から離れてよい)。R の点の列は JSON にして sha256 を記録し、
ブラウザでも同じ定数を使う。進み s は「前のフレームの s の −0.5〜+1.5 m の範囲だけを探す射影」で求め(黒シートの折り返しで飛ばないように)、
周をまたいでも増え続ける値にする。リセット時は、今の目標ゲートの前後の区間に限って最も近い点を探す。

| 番号 | 中身 | 正規化 |
|---|---|---|
| 1–3 | 速さ v、実際の舵角 δ、ヨーレート ω(= clamp(v·tanδ/0.26, ±μg/|v|)、sim-core と同じ式) | /4.5、/0.52、/4 |
| 4–5 | 前回の行動 a0, a1(フレーム 0 は 0, 0) | そのまま |
| 6–8 | R からの横ずれ e_y、向きのずれ e_ψ の sin・cos | /0.5、そのまま |
| 9–40 | R 上の Δs = 0.25, 0.5, …, 4.0 m の 16 点の位置(車の座標系: 前・左) | /4 |
| 41–56 | その 16 点の路面 μ | /0.8 |
| 57–75 | 車体の中心から −90°〜+90° を 10° おきの 19 本の距離(**高さに関係なく全障害物**。支柱の脚・ゲートの脚も含む。最大 3 m) | /3 |
| 76 | 車体の中心の路面 μ | /0.8 |
| 77–78 | 今の目標ゲートの線に対する位置(along・lateral。2.5 節の gateStatus と同じ定義) | /2、/0.65 |
| 79 | 車体の長方形と全障害物の最小距離 d_min(線分は半径つき、円、軸に平行な四角、外枠。0.5 m で切る) | /0.5 |

観測は学習中の移動平均・分散で正規化(±5 で切る)し、書き出すときに固定する。`sim.observe()` のレイは使わない
(高さ 8 cm 未満の障害物が映らないため)。時刻は観測に入れない(20 秒の打ち切りは価値の補いで扱う)。

### 2.4 行動と PWM
- 方策の出力 a ∈ ℝ²(ガウス分布。展開のときは平均)を [−1, 1] に切る。
  舵の指令 δ_cmd = 0.52·a0 [rad](正が左)、目標速度 v_cmd = V_cap·(a1 + 1)/2 [m/s]。主の `main` は V_cap = 4.5、参考の `open` は 7.24。後退はしない。
- アプリはこの {steering, speed} をそのフレームで `sim.step` に渡し、記録では PWM に直す(`dataset_recorder.py` の `action_to_pwm`):
  舵 µs = 1442 + a0·558(a0 ≥ 0、左)/ 1442 + a0·442(a0 < 0、右)、スロットル µs = 1498 − (v_cmd/7.24)·498。
  `main` ではスロットルは 1188.5〜1498 µs(教師と同じ範囲)、舵は 1000〜2000 µs。CH3 は 1500、eRPM = −2000·v。
- 正解ラベルは「適用した PWM の 1〜10 フレーム先」(`future_actions[k][j] = vehicle[k+1+j]`)。RL の行動がそのままラベルになる。

### 2.5 報酬と終了(1 フレームごと)
```
r = clip(s_t − s_{t−1}, −0.3, v_t·dt + 0.05)          進み [m](射影の飛びで得をしないよう、実際に動いた距離で上限)
  − 0.02·(a0_t − a0_{t−1})²  − 0.01·(a1_t − a1_{t−1})²   なめらかさ(ラベルのぎざぎざを抑える)
  − 0.02·max(0, ρ − 1.1)                               横の頭打ちの超過。ρ = v²·|tanδ| / (0.26·μ·g)(δ・v はステップ後の実際の値)
  − 0.05·max(0, (0.05 − d_min)/0.05)                   すき間 5 cm 未満(学生がまねできる余裕。教師は 6.1 cm)
終了(罰あり): 衝突 −10 / ゲート逃し(今のゲートの線を越えたのに |lateral| > 0.65)−10 /
              黒シート違反・周の終わりの横断なし・周の距離不足(sim の required_crossing_missing・lap_distance_insufficient)−10 /
              停止(1 秒以降に 0.2 m/s 未満が 2 秒続く)−5 / 逆走(s が直近の最大から 1 m 以上戻る)−5
打ち切り(罰なし): 20 秒(collection_duration_complete)→ 最後の観測の価値で補う
```
- 一定の時間(20 秒)で進む距離を最大にする = 平均速度を最大にする = 周回時間を最小にする。周を完走したときの賞与は置かない。
- 近道の悪用は起きにくい: ゲートは順番どおり・±0.65 m で、外すと即終了。黒シートの折り返しは 8〜13 番のゲートが通らせる。
  進みは実走行距離で上限があるので、射影の飛びは得にならない。壁沿いの走りは衝突で終わる。
- PTFE を避けてゲート 16 の外側(x > 4.04)を通るのはルールの範囲内(認める)。
- 横の頭打ちの罰は「限界まで曲がる」こと自体は罰しない(ρ ≤ 1.1 は 0)。限界を大きく超えた舵(実車ならタイヤがこすれて遅くなる操作)を抑える。

### 2.6 エピソードと開始の乱し
- エピソード = 停止から 20 秒(600 フレーム)の連続周回。記録と同じ長さ・同じモード。
- 開始: 50% はゲート 0、50% はゲート 0〜32 から一様に選ぶ。どちらも横ずれ U(−0.12, 0.12) m、向き U(−8°, 8°)。種は環境ごとに決める。
  これで、記録の 60 条件(ゲート 0・±3 cm・±3°)、頑健さの評価(±0.10 m・±6°、ほかのゲート)、閉ループ評価の開始(ゲート 20 を含む)を覆う。
- 速さを持った途中からの開始(initialState)は連続周回では使えないので使わない。立て直しの多様さは、確率的な方策のゆらぎとほかのゲートからの発進でまかなう。

### 2.7 アルゴリズム(PPO、CPU、自前の実装)
| 項目 | 値 |
|---|---|
| 方策 | 平均 = MLP 79→256→256→2(tanh)、標準偏差は状態によらない学習パラメーター(log σ の初期値 −0.7) |
| 価値 | 別の MLP 79→256→256→1(tanh) |
| 収集 | 64 環境 × 256 ステップ = 16,384 ステップごとに更新 |
| 更新 | 5 エポック、ミニバッチ 4,096、Adam lr 3e-4 → 3e-5(線形)、clip 0.2、価値の係数 0.5、エントロピー 0、勾配のノルム 0.5、KL > 0.03 で早めに止める、アドバンテージはミニバッチで正規化 |
| 割引 | γ 0.995(約 6.7 秒先まで。ブレーキの 2〜3 秒を見通せる)、GAE λ 0.95 |
| スレッド | torch 2 スレッド + Node ワーカー 4 つ(6 コア) |
| 置き場所 | `experiments/20261013_sim_rl_bestlap/rl/`(`env_worker.mjs`・`features.mjs`・`policy_forward.mjs`・`vec_env.py`・`ppo.py`・`train_rl.py`・`export_policy.py`・`evaluate_policy.mjs`) |

## 3. 「ベストラップ」の定義と妥当性

### 3.1 定義
- **停止から 1 周(lap from stop)**: 単周モード(`episodeMode` なし)、標準の開始、停止から。`state.reason == route_complete`・33/33 ゲート・
  黒シートの有効な横断がちょうど 1 回・衝突 0・距離の条件を満たし、時間は sim の `metrics.elapsed`(作者の 8.931・8.964 秒と同じ測り方)。
- **フライングラップ(flying lap)**: 連続周回 20 秒・標準の開始の `lap_events[1].elapsed`(2 周目。その周の衝突 0・黒シート 1 回・33 ゲート)。
  あわせて REC60 の 2 周目の中央値と最小値を載せる。
- 比べる相手: 教師 単周 8.9308 秒 / 連続の 1 周目 8.7584 秒(標準)・8.7097〜8.7584 秒(60 シーン)/ 2 周目 8.3701 秒(標準)・8.3589〜8.4068 秒、
  学習済み ONNX 8.964117 秒。

### 3.2 妥当性の確認(独立の再生)
- RL の方策の周(controller `demo` 相当)はユーザーの `qa/verify-learned-lap.mjs` が受け付けない(外部 ONNX・単周・標準の開始の記録だけを数える)ので、
  **同じ `sim-core.js` の上に作った同等の検証** を使う: 保存した操作列を元の `sim-core.js` で再生して軌跡が一致(差 ≤ 1e-9)し、さらに再生した軌跡から
  **自前のコードで** ゲートの通過(順番・±0.65 m)と黒シートの車幅の条件と衝突の有無を数え直して、sim の集計と一致すること(`verify_recording.mjs` を拡張)。
- JetFormer の周(外部 ONNX)は、標準の開始の単周を **ユーザーの `verify-learned-lap.mjs`** で確認する(`--model` で ONNX の sha256 を独立に指定)。
  ほかの開始・連続周回は上の同等の検証で確認する。

### 3.3 頑健さ
- 選んだ方策は REC60 の 60/60、ROB24 の 22/24 以上で成立していること(2.10 節)。
- 参考として、遅延 1 フレームでの STD の単周(教師は衝突する)と、3 本の種それぞれの結果を報告する(合否には使わない)。

### 3.4 現実味の指標(教師・実車と比べる)
REC60 と STD について、RL(`main`・`open`)・教師(Node で同じ 60 条件を再現)・実車(`clean_driving_20261011` の aligned、走行中 = 0.3 m/s 超)で計算する:
最高速・速さの 99% 点・4 m/s 超の時間の割合、横加速度(v·ω)の最大と 95% 点、横の頭打ち(ρ > 1)の時間の割合、
舵の指令の変化の速さ(|Δδ_cmd|·30 の 95% 点)と実際の舵角の変化の速さ、舵の指令が端(|δ_cmd| ≥ 0.494 rad、PWM ≤ 1063 または ≥ 1972 µs)の割合、
スロットル PWM の 1% 点、最小すき間。
- 前もって決めた注意の印: `main` の横加速度の 95% 点、または舵が端の割合が教師より 25% 以上大きければ、報告で「教師より荒い」と明記する(学習し直しはしない)。

### 3.5 「実車でできる範囲」の第 2 の変種は作らない
- `main` の速度の上限 4.5 m/s は、作者の教師の上限であり、実車の 99% 点(4.4〜4.5 m/s)とほぼ同じ。PWM で 1188.5 µs までで、教師と同じ範囲。
  高い速さでは PWM → 速さの換算が実車より速すぎる見込み(実車は 1044 µs でも 約 5 m/s)なので、4.5 を超える指令は実車で同じ速さにならない。
- 横は物理の上限 μg(カーペット 7.85 m/s²)。実車の速さ × ヨーレートの 95% 点は 約 9 m/s² で(滑りで大きめに出る)、シミュレーターの上限が実車より甘いとは言えない。
  さらに横に上限(例 0.8μg)を付けると教師(0.95μg で計画し、走ると 1.0μg)より遅くなり、「ベストラップ」の目的に反する。
- よって `main` をそのまま「実車でできる範囲」のベストラップとする。代わりに上限を外した `open`(7.24 m/s)を 1 本だけ学習し、
  「上限 4.5 で何秒失っているか」を示す参考値にする。`open` は記録しない(PWM が 1000 µs まで振れ、実車の範囲の外になるため)。

### 3.6 RL の合格基準 H1(RL が教師のベストラップを超えたか)
次をすべて満たせば「RL は教師を超えた」とする(選んだ方策、元のコアでの値):
1. STD の停止から 1 周 ≤ 8.831 秒(教師 8.931 − 0.10)。
2. REC60 の 1 周目の平均 ≤ 教師の REC60 の 1 周目の平均 − 0.10 秒、2 周目の平均も同じく 0.10 秒以上速い。
3. `main` の 3 本の種のうち 2 本以上に選べるチェックポイントがあり、その 1. の値が 8.931 秒より速い。
0.10 秒は 3 フレームで、教師の 60 シーンのばらつき(1 周目の幅 0.049 秒)の約 2 倍。

### 6.3 オフライン評価
- RL の val(12 シーン)と教師の val(12 シーン)の全フレーム(future_valid)で、S-T・S-R(・S-TR)の L1 [µs] を、舵・スロットル別に、
  1 ステップ目(走行で使う先読み 1)と 10 ステップの平均で出す(PyTorch、`runtime.load_run` の best、GPU、短い処理なので jf-heavy の big)。
- 外部の参照のオフライン L1 は任意(ONNX を CPU で、ジャンル 4 で)。

### 6.4 合格基準 H2(JetFormer がベストラップを学んだか)
T(m, e) = モデル m の開始 e での停止から 1 周の時間(完走し、検証が通ったときだけ)。
- (a) 完走: S-R の種 0・1 がどちらも E0 を完走し、ユーザーの検証器が PASS。かつ 6 条件 × 2 種 = 12 回のうち 9 回以上(75%)完走。
- (b) RL に近い: S-R の完走した回の T(S-R, e) / T_RL(e) の中央値 ≤ 1.05。
- (c) 教師で学んだモデルより速い: S-R と S-T の両方が完走した(種、開始)の組で、T(S-T) − T(S-R) の中央値 > Δ。
  Δ = max(0.10 秒, 2 × 種のばらつき)、種のばらつき = 腕ごとの |中央値_e T(腕, 種 0, e) − 中央値_e T(腕, 種 1, e)| の大きいほう。
  組が 3 つ未満なら(S-T がほとんど完走しないなど)、(c) は「S-R の E0 の時間が、両方の種とも外部の参照の E0 の時間 − 0.10 秒より速い」で判定する。
- 判定: (a)(b)(c) すべて → **「学習できた」**、(a) と [(b) または (c)] → **「一部できた」**、それ以外 → **「できなかった」**。
- 参考(合否に使わない): フライングラップ、6.3 節の L1、S-TR、外部の参照との差、S-R 種 0 の E0 でゲインを変えたとき(前進 1.01、舵 0.95・1.05)。
