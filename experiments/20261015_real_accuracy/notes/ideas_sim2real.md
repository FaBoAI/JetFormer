## 0. 結論(先に)

1. **シミュレーターの画像と実機の画像は、モデルの中ではまったく別物です。** 画像の背骨の特徴で、線形の分類器が 99.8〜100% 見分けます。
   明るさ・コントラスト・彩度・ぼけを実機に合わせても(見た目合わせ T)、違いは 13〜22% しか縮まりません。
   実機だけで学んだ A に、シミュレーターの画像を見せたときのステアの誤差は 166 µs で、「いつも真ん中の値を出す」だけの 159 µs より悪いです。T をかけると 174 µs と、さらに悪くなりました。
   → **違いは色や明るさではなく中身(床の粗い模様・壁・カーテン・動きのぶれ)です。学習の側の色合わせでは埋まりません。**
2. **混ぜて学習したときの損は、ステアから来ています。** ステアの誤差は C で +0.6 µs、C-DIV で +1.6 µs 増えました。スロットルは同じくらいです(−0.2〜+0.3 µs)。
   低速の直線(HS、627 フレーム)では、ステアもスロットルも 6〜7 µs 悪くなっています。
   「C-DIV のステア + A のスロットル」を組み合わせても 50.1 µs で、A(49.3)より良くなりません。「シミュレーターはスロットルだけ、またはステアだけを教える」という案は、この結果で見込みが無くなりました。
3. **シミュレーターが役に立つ形は 1 つだけ見えました。平均の相手(アンサンブル)です。** ただし、効いているのはシミュレーターではなく「2 本を平均すること」そのものです。
   - A と C(混ぜて学習)を平均すると 48.31 µs、A と C-DIV では 48.43 µs でした。どちらも、A の別の種と平均した 48.34 µs と同じです。
   - **それよりはっきり効くのは、形の違う方策との平均です。** v0 と TransFuser多段型(msfusion)の平均は 46.99 µs(−2.3 µs)で、best でも last でも規則の閾値を越えました(後から選んだ組なので、確かめ直しが要ります)。
   - 方策 5 つの平均は 46.40 µs(−2.9 µs)でした。そこにシミュレーターの腕を足すと、少し悪くなりました。
4. **49 µs は「固い底」ではありません。** 種による予測の違いは L1 で 17.8 µs あり、そのうち平均で消える分が約 1〜3 µs です。
   同じ形のモデルを無限に平均したときの見積もりは約 47.4 µs、形の違う 5 つでは 46.4 µs です。残りの約 46 µs は、人の周ごとの揺れと、モデルの偏りです。
   **どの案でも、得られるのは数 µs まで** です。実用上の目安の 10 µs には届かない見込みです。
5. ついでに分かったこと: 間引き 3 で学習しない位相のフレームでも、誤差は大きくありません(A 種 0: 位相 0 / 1 / 2 で 49.30 / 49.32 / 48.82 µs)。シミュレーターで見えた「IMU の位相」の問題は、実機の主指標では損になっていません。

## 2. 案(順位つき)

### E1 平均の相手 — シミュレーターの腕・形の違う方策を平均し、1 つのエンジンにまとめる(1 位)

- **何を**: 別々に学習した 2〜3 本のモデルの出力 [10, 2] を平均します。
  - 走行のコードを変えないよう、`torch.nn.Module` で包んで平均を出す 1 つの ONNX にします。入力は今と同じ(画像・ToF・IMU・操作値・ジャンル)です。
  - ジャンル数の違う相手(C・C-DIV は 9、A は 6)は、包みの中でジャンルの one-hot の前の 6 つを切って渡します。
  - これを 1 つの TensorRT FP16 エンジンにします。速さの見込みは v0 2.4 ms + msfusion 3.1 ms で約 5.5 ms です。今の 33 ms の枠に入ります。
- **根拠**(1.1):
  - シミュレーターの腕との平均は best で −0.9〜−1.2 µs でした。ただし A の別の種との平均(−0.96)と同じで、**シミュレーターならではの効き目は 0 ± 0.3 µs** です。
  - 形の違う方策との平均が一番効きました(v0 + msfusion −2.3 / −2.2、5 つで −2.9 / −2.7。best・last とも規則を満たす)。別のフレーム(part 1)でも同じ向きでした。
  - シミュレーターの担当としての答えは「混ぜた腕は平均の相手にはなるが、msfusion のほうが良い相手」です。
- **確かめ方**(後から選んだ組なので、新しい種で確かめ直す):
  1. msfusion を種 2・3 で新しく学習します(1 本 約 30 分 + エンジン 4 分)。
     コマンドは 10/12 と同じで `tools/train.py --policy msfusion --data data/datasets/clean_driving_20261011 --epochs 30 --lr 3e-4 --stride 3 --batch 64 --no-command-input --impact-g 2.5 --seed {2,3}`、
     run 名は `realacc_20261015-ensmsf-s{2,3}` です。
  2. 腕 E1 の「種」は E1-0 = v0 種 0 + msfusion 種 2、E1-1 = v0 種 1 + msfusion 種 3 とします(どちらも組を選んだ後に学習するので、選んだ偏りが入らない)。
     予測は `tools/sim_cotrain_eval.py` の道具(`policy_zoo._predict_frames`)で、新しい 2 本の best・last を出し、平均は CPU で取ります。
  3. 判定は 10/13 の規則のままです。2 組とも A の 2 本の小さい方より小さく、平均の改善が best で 0.626 µs・last で 1.322 µs を越えれば「良い」。
     シミュレーターの相手(A + C-DIV)も同じ表に並べます(参考。予測は済み)。
  4. まとめた ONNX → FP16 エンジンのゲート(PyTorch との差 ≤ 2.5 µs、run_numpy の中央 ≤ 8 ms)を確かめます。
- **リスク**:
  - 推論が約 2.3 倍になります(エンジンのメモリも増える)。
  - 走行の後処理(ゲイン・先読み)は、1 本のときの値で合わせてあります。
  - 平均は予測をなめらかにするので、R1 の右いっぱいの合図が弱まるおそれがあります。R1・DE の通過の値も一緒に見ます。
  - 10 µs の実用上の差には届きません。

### E2 平均を 1 本に蒸留する(2 位)

- **何を**: 平均のモデル(先生)の予測を正解に混ぜて、v0 を 1 本学習します(`target = α·人 + (1−α)·先生`、α = 0.5)。推論の重さは今と同じです。
- **根拠**:
  - 平均で −1〜−3 µs 縮みました(E1)。誤差には「種による揺れ」が 17.8 µs あり、蒸留はそれを 1 本に移す標準の手です。
  - ただし、**学習のフレームでの先生の予測は、ほぼ人の正解を覚えています**(学習の誤差 14 µs)。そのままでは「人の正解で学ぶ」のとほとんど同じです。
- **確かめ方**:
  1. 先に安い確かめをします(GPU 約 5 分)。先生の学習のフレームでの誤差が 20 µs より小さければ、覚えています。
     その場合は、学習の 41 シーンを 2 つに分けて、片方で学んだ先生にもう片方を予測させます(v0 + msfusion × 2 つの分け = 4 本、半分のデータなので 1 本 約 10〜15 分)。
  2. 生徒(v0、種 0・1、`realacc_20261015-kd-s{0,1}`)を学習します。実験のフォルダーの包み(`train.py` の `JetFormerDataset.__getitem__` で target を差し替える。30 行ほど)を使います。
  3. 判定は 10/13 の規則です。
- **見込み**: −0.3〜−1.0 µs(不確か)。先生にシミュレーターの腕を入れるかどうかは、E1 の結果で決めます(今の数字では入れる理由が無い)。

### E3 シミュレーターの画像を消して混ぜる(シミュレーターは ToF・IMU・回転数だけで教える)(3 位)

- **何を**: C-DIV と同じデータ・同じ作り方で学習します。ただし、ジャンル 8(シミュレーター)のフレームだけ、画像を「正規化の後の 0」(一様な平均の色)にします。
  - 実験のフォルダーの包みで `JetFormerDataset.__getitem__` を差し替えます(20 行ほど)。
  - 画像の枝(ResNet)は実機の画像だけで学びます。シミュレーターは ToF・IMU・回転数の道と、合流した後の層だけを動かします。
- **根拠**:
  - 混ぜたときの損はステアから来ています(1.1)。シミュレーターの画像は、実機にまったく移りません(1.2: A のステアが真ん中の値より悪い。分類器が 100% 見分ける)。
  - ならば、シミュレーターの画像は「食い違いの元」だけです。ToF は両方でよく似ています(10/13 の表)。
  - 副次の見込み: C-DIV は画像が無いときの誤差が A の約半分でした。カメラが止まったときの強さが、さらに上がる見込みです。
- **確かめ方**:
  1. 種 0・1(`realacc_20261015-simnoimg-s{0,1}`)を学習します。C-DIV と同じ 30 エポック・lr 3e-4・間引き 3・`--no-command-input`・`--impact-g 2.5` で、腕のフォルダーも C-DIV のもの(シンボリックリンク)を使います。
  2. 判定は、A と比べるとき 10/13 の規則、C-DIV と比べるとき 10/15 の閾値(best 0.954・last 1.322)です。
  3. 参考として、画像を消したときの誤差(1.2 の表と同じ測り方)と、HS のステアを並べます。
- **見込み**: 0〜−0.3 µs。A を越える見込みは小さく(「良い」の確率 約 10%)、ねらいは「混ぜても損をしない」形を作ることです。

### E4 見た目合わせ(T)をしたシミュレーターで混ぜる(4 位・今は勧めない)

- **何を**: C-DIV の作り方で、シミュレーターの画像に T2(ぼけ・ヒストグラム合わせ・彩度)と動きのぶれをかけて学習します。
- **勧めない理由**(1.2):
  - 数の上では実機に合っても、モデルの中の違いは 13〜22% しか縮みません(分類器は 99.8% のまま)。
  - 実機だけの A のステアは、T をかけたほうが悪くなりました(166 → 174 µs。真ん中の値 159 µs)。
- **やるなら描画の側で**: シミュレーターの床の模様・壁・柵を実機の写真から取ること、動きのぶれ、カメラの高さ・向き・画角を合わせることです。
  これはユーザーのシミュレーター(sim-core.js の描画)の作業で、学習の側の 1 日の試しには入りません。
  直したかどうかは、`probe_domain_gap.py` の「見分けられる率」と「A のステアの誤差(真ん中の値 159 µs より下がるか)」で、学習の前に安く確かめられます。

### E5 見分けを邪魔する学習(GRL)・シミュレーターの補助の正解(5 位・今は勧めない)

- **何を**:
  - (a) 画像の特徴にシミュレーターと実機を見分ける頭を付け、勾配を逆にして見分けにくくします(DANN)。
  - (b) シミュレーターでしか取れない正解(壁までのすき間・衝突までの時間・コース上の位置)を補助の出力で学ばせます。
- **勧めない理由**:
  - 違いが大きすぎます(分類器 100%)。特徴を無理に重ねると、実機での見分けに要る情報まで消すおそれがあります。
  - 補助の出力は、10/12 の TCP(通過点・目標速度)でも主指標を変えませんでした(49.73 µs)。
  - 学習の包みと損失のコード(60〜100 行)が要り、GPU も 1 本 約 55 分かかります。

### やらなくてよいこと(すでに答えがある)

| 案 | 答え | 根拠 |
|---|---|---|
| シミュレーターはステア(またはスロットル)だけ教える | 効かない | 組み合わせ C-DIV のステア + A のスロットル = 50.11 µs。A のステア + C-DIV のスロットルは 49.23 µs(−0.07) |

## 3. 学習の前に固定する規則の案(E1〜E3 共通)

- **主指標**: 10/13 と同じ 4,670 フレーム・L1・best と last。「良い」は 2 つの種(E1 は 2 つの重ならない組)がどちらも A の 2 本の小さい方より小さく、平均の改善が best 0.626 µs・last 1.322 µs を越えること。「悪い」はその逆。ほかは「同等」。
- **E1 の追加**: 組は学習の前に決めます(v0 種 0 + msfusion 種 2、v0 種 1 + msfusion 種 3)。後から組を替えません。エンジンのゲートに落ちたら「走行には使えない」と書きます。
- **参考(判定に使わない)**: ステア・スロットル別、HS、part 1(交代の後の人の修正)、画像を消したときの誤差、R1・DE の通過の値。
- **実用上の差 10 µs**: どの案も届かない見込みです。「良い」になっても、実車の A/B/A の候補にするかは、ユーザーと決めます。
  候補にするなら、10/12 のカード 1(モデル B だけの A/B/A)の形で「B → 平均のエンジン → B」とします。
