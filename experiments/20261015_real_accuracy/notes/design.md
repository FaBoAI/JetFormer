**天井の見積もり(期待値の目安)**
- 「人が同じ場所・同じ状態で別の周に出す操作の差」から見積もった底は 22〜44 µs で、中心は約 31 µs です。

- 「良い」が出ても、走行の推奨をモデル B から替える根拠にはなりません。実車の A/B/A の候補にするだけです。

## 1. いま分かっていること

### 1.1 49 µs は何でできているか(案出しの段の下調べ。どれも保留の 4,670 フレームを見たあとの数字)

**電池のシーン**
- 高速の保留シーン `20261010-193638-0003`(573 フレーム、12%)は、誤差全体の 24% を占めます。L1 は 96.7 µs です。
- 後半は、人がスロットルをいっぱいにしても eRPM が 2,000 まで落ちています。電池が減って、同じスロットルで出る速さが落ちたと見られます。
- モデルは今の操作値を入力に入れないので、この「車の効きの低下」を知る手段がありません。
- このシーンを除くと、A は 42.49 / 42.91 µs です。

**モデルどうしの食い違い(ばらつき)**
- 予測の違いは、同じ形の種どうしで 17.8 µs、v0 と msfusion で 27〜29 µs です。
- 平均すると誤差が下がります。
  - v0 の種 0 + 種 1: 48.34 µs(−0.96)
  - v0 + msfusion(同じ種どうし): best 46.82 / 47.16 µs(−2.31)、last 47.36 / 47.25 µs(−2.19)
  - 10 本の平均: 46.10 µs

**短い先の誤差**
- 1 フレーム先のステアでも 41.6 µs あります。「今の人の操作をそのまま続ける」予測では 15 µs です。
- 短い先の誤差の多くは、今の操作を入力に入れない設計から来ています。この設計は copycat を避けるためのもので、今夜は変えません。

**効いていないもの**
- 間引きの位相: 位相 1・2 − 位相 0 = +0.10 µs
- ラベルの時間のずれ: どのモデルもずれ 0 がいちばん合います
- 一定の偏りの補正: シーンを抜くと +2.7 µs 悪くなります
- best と last の平均: −0.03 µs
- シミュレーターの見た目合わせ: 特徴の上では 99.8% 見分けられたままです
- C-DIV のステア + A のスロットル: 50.1 µs

## 2. 腕の選び方

### 2.1 選んだもの

- **ENS**: 下調べでいちばん大きく、11 シーン中 10 で効きました。介入の集合でも同じ向きでした。学習の作り方は今と同じで、走行のコードも変えずにエンジン 1 つにまとめられます。種 2 本 × 2 つの形を新しく学習し、組を先に固定して確かめます。
  - 対照として、同じ形の平均(SAME = v0 の種の平均)も並べます。「形が違うから効く」のか「平均したから効く」のかを分けるためです。
- **SIZE**: 「実機のきれいな走行を増やせば下がるか」は、まだ誰も測っていません。シミュレーターは画像の差で効きませんでした(10/13・10/15)。
  - データを集めるのはユーザーなので、その判断材料になります。1 本 8〜13 分と安い腕です。
- **ROT**: 捨てていた 2/3 のフレームを、学習の時間を増やさずに使います。変えるのは 1 か所だけです(検証・学習率・エポック数は同じ)。見込みは小さいですが、学習の作り方の側の案で一番きれいに試せます。
- **Z(学習なし)**: GAIN(電池の効きの補正)、TE(時間方向の平均)、SEED-ENS です。保存済みの予測で 0 分で済みます。新しい種にも同じように当てはめて、「別のモデルでも同じ向きか」を見ます。
  - GAIN は、実車で電池が減っても遅くならない機能の候補です。主指標の改善は 1 シーンから来ているので、「ほかのシーンを悪くしないか」と「介入の集合を悪くしないか」を害の確かめにします。

### 2.2 選ばなかったもの(理由)

| 案 | 選ばない理由 |
|---|---|
| E2 平均を 1 本に蒸留 | 先生は学習のフレームを覚えています(学習の誤差 14 µs)。交差で作った先生が 4 本要り、GPU が約 3 時間かかります。見込みは −0.3〜−1.0 µs で不確かです。ENS が「良い」でゲートに落ちたときの、次の候補にします |
| E3 シミュレーターの画像を消して混ぜる | ねらいは「混ぜても損をしない」ことで、実機の精度の改善ではありません(「良い」の見込み 約 10%)。カメラが止まったときの強さの話として、別の日にします |
| E4 見た目合わせ・E5 ドメインの見分けを邪魔する学習(GRL)・補助の正解 | 下調べで見込みが無いと分かりました(見分けられる率 99.8%、A のステアがシミュレーターで定数の予測より悪い、TCP の補助の正解も効かなかった) |
| 強めの揺らし + EMA をまとめた腕 | 10/13 にずれへの強さは上がりましたが、精度は変わりませんでした。重みの平均の目安も −0.03 µs でした。3 つを混ぜると、どれが効いたか分かりません |
| 今の操作値を入力に入れる | 指標は大きく下がります(1 フレーム先のステア 15 µs)。ただし、走行では自分の出力をなぞる(copycat)おそれがあります。設計の約束(--no-command-input)なので、今夜は変えません |
| Huber・MSE の損失、未来のステップの平滑化、ラベルの時間合わせ、長く学習、一定の偏りの補正、ジャンル別の重み | 下調べで効かないか、悪くなる向きでした(`ideas_data.md` §2 の表) |
| 3 本以上の平均 | 4 本(+tcp・act)は −2.40 で、2 本(−2.31)とほぼ同じです。推論の時間だけ増えます |

### 3.2 SIZE(実機のデータの量の曲線)— 判定ではなく測定

- **部分集合**: 学習の 41 シーンから選びました(`experiments/20261015_real_accuracy/size/make_size_masks.py`、乱数の種 20261015)。
  - ジャンル別に、ログを回しながら並べます。その先頭から、学習サンプル数がジャンル全体の f 以上になるまで取ります。
  - 入れ子です(Q ⊂ H ⊂ T ⊂ 全部)。
  - 数えたあと、Dataset を作って同じ数になることを確かめました(`protocol/check_rot_size.py`、検証は A と同じ 1,559)。

| 名前 | シーン数 | 学習サンプル | 全体に対する割合 | 高速の割合 |
|---|---|---|---|---|
| Q | 11 | 1,682 | 0.285 | 0.41 |
| H | 20 | 3,046 | 0.515 | 0.39 |
| T(任意) | 32 | 4,682 | 0.792 | 0.39 |
| 全部(= A) | 41 | 5,912 | 1 | 0.38 |

- **学習**: A と同じコマンドに `--drop-mask experiments/20261015_real_accuracy/size/size_{Q,H,T}.npz` を足します。種 0・1 です。
  - 順番は sizeH-s0 → sizeH-s1 → sizeQ-s0 → sizeQ-s1 です(任意で sizeT-s0・s1)。
  - エポック数は 30 のままです(データが少ないほど勾配のステップは少なくなります。報告に書きます)。
- **出すもの**
  - L(Q)・L(H)・L(全部 = A)を、2 つの種の平均で出します(best と last、主指標・電池のシーンを除いた値)。
  - 2 倍にしたときの改善の見込みを、次の 2 つで出します。
    - log2 N あたりの傾き: s1 = (L(Q) − L(H)) / log2(N_H/N_Q)、s2 = (L(H) − L(全部)) / log2(N_全部/N_H)
    - **G2_lin = s2**: 平らにならないと仮定した、楽観の上限
    - **G2_pow = s2 × clip(s2/s1, 0, 1)**: 同じ割合で平らになると仮定した、控えめの値
  - 誤差の幅は、val の 11 シーンのブートストラップ(2,000 回・種 0)で出します。
- **読み方**(固定)

| 条件 | 読み |
|---|---|
| L(H) − L(全部) ≤ 0.626 µs(best)、または G2_lin < 1 µs | 「データを 2 倍にしても 1 µs 未満の見込み。精度のために録画を増やす価値は低い」 |
| G2_pow ≥ 2 µs | 「2 倍で 2 µs 以上の見込み(ENS と同じくらい)。きれいな周回の録画を勧める(電池の残りも記録)」 |
| ほか | 「1〜2 µs の見込み(中くらい)」 |

- 電池のシーンを除いた値でも同じ計算をして、並べます。

### 3.3 ROT(間引きの位相をエポックごとに回す)

- **コード**: `experiments/20261015_real_accuracy/train_rot.py`(sha256 は protocol.json)。tools/train.py をそのまま読み込み、学習の Dataset の行の選び方だけを差し替えます。
  - 学習の Dataset は stride 1 で作り、「フレーム番号 % 3 == 位相」の行だけを使います。
  - 位相 = (エポック − 1 + 種) % 3 です。種 0 なら、1 エポック目の行は A とまったく同じです。
  - 検証の行と、best の選び方は A と同じです。
  - 確かめたこと(CPU): 位相 0 = A の 5,912 行と一致します。位相 1・2 は 5,903・5,879 行で、3 つは重なりません。合わせると stride 1 の 17,694 行と一致します。検証は A と同じ 1,559 行です。
- **動作確認**(GPU、学習の前に 1 回): `--epochs 2 --max-steps 2` で、`rot_log.jsonl` に位相 0・1 が出ることを確かめます。確かめたら出力のフォルダーは消します。

```
/home/jetson/bin/jf-heavy --mem 3G --lock big --need-mb 3200 -- nice -n 10 python -u experiments/20261015_real_accuracy/train_rot.py \
  --policy jetformer_v0 --data data/datasets/clean_driving_20261011 --out /home/jetson/jetformer/data/runs/realacc_20261015-rot-s0 \
  --epochs 30 --seed 0 --stride 3 --batch 64 --lr 3e-4 --workers 4 --no-command-input --impact-g 2.5
```

- 種は 0・1 です。判定は主指標の規則で A と比べます。
- 参考として、同じ種どうしの差(ROT_s − A_s)と、2 つの種の予測の食い違い(A は 17.8 µs)を出します。ばらつきが減ったかの目安です。
- 「良い」になったときだけ、エンジンを作ってゲートを確かめます(約 5 分)。

### 3.4 ENS のエンジンのゲート(GPU 約 15 分)

1. `experiments/20261015_real_accuracy/ens/` に置く道具で作ります。
   - v0-s2 と msf-s2 の best.pth を読み込みます(runtime.load_run)。
   - 2 本の出力 actions の平均を返す 1 つのモジュールにします。入力の名前と形は v0 と同じです(image・tof・imu・state・mode、出力 actions [1, 10, 2])。
   - ONNX に書き出し、`tools/build_engine.py` で FP16 のエンジンにします。
2. 成果物は `experiments/20261015_real_accuracy/ens/` に置きます。data/runs には置きません(走行の一覧に出さないため)。
3. 確かめ方は 10/12 の engine-check と同じです。

### 3.5 Z: 学習なしの確かめ(CPU、0 分。新しい予測が出るたびに当てはめる)

**GAIN(電池の効きの補正)**
- 式は `ideas_data/probe_gain.py` の既定値です(下調べの説明に、結果を見る前に書いてあった値)。
  - 効きの比 g = (1498 − 今のスロットル) / (前進 eRPM / 1000)。前進 eRPM > 2,000 で、2.5G の衝突の前後でないフレームだけを使います。
  - 同じシーンの過去 **5 秒**(今のフレームを含む)の g の中央値を g_t とします。30 フレーム未満なら補正しません。
  - g_ref はジャンル 4 で 36.41、ジャンル 5 で 36.86 です。
  - 予測のスロットルが前進側(< 1498)のときだけ、1498 − (1498 − 予測) × clip(g_t / g_ref, 0.8, 2.0) に直します。
- 10 秒の窓は、ほかのシーンで害が少なく見えます。ただし後から見た値なので、参考の行にとどめます。
- 実車のカード用に、clip の上限を 1.3 にした値も参考に出します。
- 介入の集合(part 1)にも同じ式を当てはめます。データは intervention_val の aligned です。
- **判定**: 「元のモデル」と「補正したモデル」を、同じモデルの組で比べます(GAIN は後処理なので、同じモデルどうしの比較になります)。
  - G1(主指標): 次の 2 つの組の両方で、主指標の規則で「良い」になること
    - 組 (i) A の 2 本(結果は既知)
    - 組 (ii) 新しい v0-s2・v0-s3
  - G2(害): 電池のシーンを除いた 4,097 フレームで、どちらの組でも「悪い」(閾値 best 1.134・last 1.980)にならないこと
  - G3(拒否権): 介入の集合で「悪い」(閾値 best 3.458・last 4.858)にならないこと
  - G1〜G3 をすべて満たせば、実車の A/B/A のカードの候補にします(電池が新しいときと、減ったときの両方)。

**TE(時間方向の平均)**
- 走行タブの「予測の重ね合わせ」と同じ計算です(jetformer/policies/ensemble.py の TemporalEnsembler)。
  - 設定は ensemble_j = 2、ensemble_m = 0(一様)です(ideas_data で先に決めた J=2 一様)。
  - 表の中で、同じシーンの 1・2 フレーム前の予測を使います。無い行は飛ばして、重みで割り直します。
- 判定は GAIN と同じ形です。T1(組 (i) と (ii) の両方で「良い」)と、T3(介入の集合で「悪い」にならない)を見ます。
- 満たさなければ、走行の既定(オフ)のままにします。下調べでは「同等」で、介入の集合でも悪くなる向きでした。

**SEED-ENS**
- 同じ形の 2 本の平均です。§3.1 の SAME の行にあたります。

## 5. 結論の書き方(固定)

1. 腕ごとに、「良い / 同等 / 悪い」と実用上の差(10 µs)を書きます。後から選んだ数字(下調べの値)は、判定と別の段に「下調べ(見たあと)」と書いて分けます。
2. **ENS** の書き分け:
   - 「良い」かつ ENS vs SAME も「良い」→「形の違う 2 本の平均で精度が上がった。同じ形の平均より上」
   - 「良い」だが ENS vs SAME は「同等」→「平均で上がった。形の違いの上乗せは言えない」
   - 「同等」→「下調べの −2.3 µs は新しい種では確かめられなかった」
3. **FRESH-A** が「同等」でなければ、「A の 2 本は種のばらつきを小さく見ていた可能性」と書きます。
   - そのときは、s_A' = {A_s0〜s3, B} の範囲で同じ判定をやり直し、感度として並べます。主の判定は変えません。
4. **SIZE** は、§3.2 の読み方の 3 つのうちどれかを書きます。ユーザーへの「録画を増やすか」の勧めは、この読みだけで決めます。
5. **GAIN・TE** は §3.5 の条件で書きます。GAIN は、主指標の改善がほぼ 1 シーンから来ていることを必ず添えます。
6. **走行の推奨をモデル B から替える**のは、次をすべて満たす腕だけです(10/13 の規則 4)。
   - 「良い」かつ実用上の差(≥ 10 µs)
   - ゲート合格
   - 崩れなし
   - 拒否権なし

   10 µs 未満の「良い」は「机上の小さな改善」と書きます。推奨はモデル B のままにして、A/B/A のカードの候補にします。
7. どの結論も、開いたループ(保留の記録)での結果です。実車の走りが良くなったことは示しません(10/12 の規則 7)。
