# 実機の精度に効く方策の案と「下げられる余地(天井)」の見積もり(2026-10-15)

> **依頼**: 「また、実機の精度に効く方策を考えて、トライして」。この文書はその第 1 段(案出しと測定)です。
> **対象**: 保留した実機の人のきれいな走行(clean_driving_20261011 の val 11 シーン・4,670 フレーム)の L1(10 フレーム先までのステア・スロットル)。
> 基準 A = TransFuser軽量型(JetFormer v0)種 0・1 = 49.146 / 49.457 µs(平均 49.30)。判定の規則は 10/13 に固定したもの(閾値 best 0.626 µs・last 1.322 µs、両方の種で良いこと、実用上の差 10 µs)。
> **この段でしたこと**: CPU だけ(学習・GPU なし)。今までの全モデルの予測(38 本、`data/zoo/`)と生ログを読み直しただけです。実車は動かしていません。

---

## 0. 結論

1. **49 µs は「底」ではなさそうです。** 同じ場所・同じ車の状態での「人どうしの差」から見積もった底は **約 31 µs(幅 22〜44 µs)** です。今あるモデルを平均するだけでも **46.1 µs** まで下がることを確かめました。ただし、確かめられた改善は 3 µs(6%)までで、10 µs の実用上の差には届いていません。
2. **誤差は 1 つのシーンに偏っています。** 高速の val シーン `20261010-193638-0003` は、フレームの 12% ですが、誤差全体の **24%** を占めます(L1 96.5 µs、スロットルは 140 µs)。このシーンでは、同じスロットルで出る速さが同じログの前のシーンより約 25% 落ちていました(2.67 → 1.99 m/s)。**バッテリーの電圧低下などで「駆動の効き」が落ちた**と見られます。このシーンを除くと、A は 42.5〜42.9 µs です。
3. **お金のかからない試し(CPU だけ、予測の平均)の結果**
   - **2 つの形のアンサンブル(v0 + TransFuser多段型、同じ種の組)**: 46.82 / 47.16 µs。best で −2.31 µs、last で −2.19 µs。両方の種が A の 2 本より小さいので、固定した規則なら「良い」です。ただし後から選んだ組です。
   - **時間のアンサンブル**(過去のフレームが同じ時刻を指して出した予測を平均する。推論は増えない): −0.78 µs。best では「良い」ですが、last では閾値 1.322 µs に届かないので、規則では **「同等」** です。しかも介入の集合(人が AI から取り上げて直した場面)では +1.0〜1.5 µs **悪化**しました。反応が遅れる向きなので、**採用しません**。
   - **駆動の効きでスロットルを直す**(物理の素朴な式、パラメータなし): A 種 0 は 49.146 → 47.39 µs、種 1 は 49.457 → 47.79 µs。効いたのは問題のシーンだけで(96.7 → 71.3 µs)、ほかのシーンは少し悪くなりました(42.49 → 44.06 µs)。学習で入力に入れる価値がある、という証拠です。
4. **推す順(期待できる改善 ÷ GPU の分)**:
   - ① 2 本のアンサンブルを新しい種で確かめる
   - ② 駆動の効きを入力に入れる
   - ③ 間引きで捨てている 2/3 のフレームを使う
   - ④ データ量の学習曲線を測る(実機の追加の録画が効くかの判断材料)
   - ⑤ 時間のアンサンブル(試し済み・不採用)
   - 詳しくは 4 章。

## 1. 天井(下げられない誤差の底)の見積もり

### 1.1 やり方
- **場所**: 人のきれいな 52 シーンの各フレームを、コース図の上に置きました。
  - 道具は `tools/course_fit.py` の 1 段目の当てはめ(`fit_log_stage1`)です。ジャイロの向きとホールセンサーの距離をコース図の基準線と照合し、壁と基準線への引き寄せで補正します。
  - 得られる値は、1 周の中の進み sp [m]・横ずれ [m]・向きです。
  - 9 本のログを 42 区間に分けて当てはめ、40 区間で当てはまりました(外れた 2 区間は、止まっていた 202633 の短い区間)。val の行の 99.1% で場所が付きました。横ずれの中央値は 0.18 m、基準線との向きの差の中央値は 10.9° です。
  - カメラの目印は使っていないので、場所に数十 cm の誤差はありえます。誤差があると「人どうしの差」は大きめに出るので、底は高めに見積もる向きです。
- **人どうしの差 D**: val の各フレームについて、学習のシーンの「同じジャンル・±0.30 m の中・別の周」のフレームと組を作り、|y − y'|(10 フレーム × 2 の平均)を測りました。
  - 組は「状態の近さ δ」ごとに分けて平均します。δ は、横ずれ・向きのずれ・速さ・ヨーレート・曲率・100 ms 前からのヨーレートの変化・進みの差を、標準化してまとめた距離です。
  - δ → 0 に外挿した切片 **D0** が、「同じ場所・同じ状態で、人が別の周に出す操作の差」です。
- **D0 から底 B へ**: 同じ条件から独立に 2 回引いた値の差について、どんな分布でも D0/2 ≤ B ≤ D0 が成り立ちます。正規分布なら B = D0/√2、ラプラス分布なら B = D0/1.5 です。

## 2. 誤差の内訳(どこが効いているか、`breakdown.json`・`free_combo.json`)

- **フレーム先(k)ごと**: A 種 0 のステアは k1 41.6 → k10 55.9 µs、スロットルは 42.1 → 51.2 µs です。
  - 「今の人の操作をそのまま続ける」予測は、k1 のステアが **15.3 µs** です。L1 全体では 50.6 µs で、A とほぼ同じです。
  - 短い先の誤差の多くは、**今の操作をモデルが知らない**こと(今の操作値を入力しない設計)から来ています。
  - 操作値を入力に入れれば指標は下がりますが、走行では自分の出力をなぞる(copycat)おそれがあります。指標のためだけに入れるのは勧めません。
- **ジャンル**: 高速(4)は 60.7 µs(スロットル 69.6)、低速(5)は 41.3 µs です。
- **シーン**: 26.8〜96.5 µs と大きく違います。`193638-0003` だけで誤差の 24% です(2.2 節)。
- **場所**:
  - LH(R1 の前の左ヘアピン): 63.7 µs、誤差の 23.8%
  - R1: 55.3 µs
  - GM: 52.8 µs(ステア 63.4)
  - HS: 48.6 µs
  - DE: 37.4 µs
  - 誤差の大きい上位 10% の行が、誤差の 29% を占めます。

### 2.2 `193638-0003` で何が起きたか

| | 193638-0003(val) | ほかの高速のシーン |
|---|---|---|
| 人のスロットル(3 フレーム先の中央値。小さいほど強い前進) | **1221 µs** | 1301 µs |
| A の予測 | 1332 µs | — |
| 速さの中央値 | 2.25 m/s | 2.62 m/s |
| スロットル 1255〜1285 µs のときの速さ | **1.99 m/s** | 同じログの 0002: 2.67 m/s |
| 駆動の効きの比(学習の中央値 ÷ 直前 5 秒の値) | **1.59** | 0.89〜1.11 |

- 人は強く踏んでいるのに、遅くしか走っていません。駆動の効き(速さ ÷ スロットルの深さ)が約 37% 落ちています。
- 同じ傾向は、ほかのログの終わりにもあります(150424 の 0004・0005、200916 の 0007 以降)。バッテリーの電圧低下が一番ありそうな理由です。VEHICLE に電圧の記録が無いので、確かめてはいません。
- モデルの入力(画像・ToF・IMU・回転数)には「効き」が入っていません。今の設計では当てられない誤差です。
- 実車でも、バッテリーが減ると AI の走りが遅くなる原因になりえます。

## 3. 指標の提案(飽和していて、走りの質を映すもの)

| 指標 | 今の値(A) | 飽和しているか・使い方 |
|---|---|---|
| ステアの向きの正解率(3 フレーム先、\|人 − 中心\| > 50 µs) | 0.984 / 0.980 | **飽和**。差が出ないので判定には使わない |
| **主指標 L1**(固定した規則) | 49.30 | 今までの判定と比べられるように残す |
| L1(`193638-0003` を除く) | 42.49 / 42.91 | 副。1 つのシーン(効きの変化)に引っぱられない値。駆動の効きの案では、両方を出す |
| 3 フレーム先(走行で実際に使う値)のステアの L1 | 47.8 / 48.6 | 副。走りに直接効く値。時間のアンサンブルで 1 µs 動いた |
| 介入の集合の L1(1,570 フレーム、人が AI から取り上げて直した場面) | 128.9 / 127.8 | 副。立て直しの反応を見る。種どうしで最大 10 µs 揺れる(msfusion 129.7 / 119.9)ので、悪化の「拒否権」として使う(+1 µs 以上そろって悪化なら印を付ける) |
| 場所別の L1(LH・GM・R1) | 63.7・52.8・55.3 | 副。難しい場所の改善が見える |
| R1・DE の窓(10/12 から) | — | 種どうしで 7.7 / 2.8 µs 揺れるので、参考のまま |
| **底からの超過**(L1 − 31 µs) | 約 18 | 説明用。「どれだけ詰められる余地が残っているか」 |

- 判定は今の主指標と規則のままにします。副指標は、悪化の印(拒否権)と説明に使います。
- 特に「介入の集合で悪化」は、閉じたループで反応が遅れる印なので、実車の候補から外す理由にします。今日の時間のアンサンブルがこれにあたります。

## 4. 方策の案(期待できる改善 ÷ GPU の分の順)

### ① 2 本のアンサンブル(TransFuser軽量型 v0 + TransFuser多段型、同じ種の組)
- **証拠(今ある予測、CPU)**

  | 組 | best(種 0 / 種 1)[µs] | last(種 0 / 種 1)[µs] | A との差 best / last |
  |---|---|---|---|
  | v0 + 多段型 | 46.82 / 47.16 | 47.36 / 47.25 | −2.31 / −2.19 |
  | v0 + DINOv2型 | 47.28 / 47.42 | 47.55 / 48.00 | −1.95 / −1.72 |
  | v0 種 0 + v0 種 1 | 48.34 | — | −0.96 |
  | 10 本(5 つの形 × 2 つの種) | 46.10 | — | −3.2 |

  - 介入の集合でも良くなりました(125.6 / 119.2 µs vs 128.9 / 127.8)。
  - 同じ形の種を足すより、**違う形を混ぜる方が効きます**。v0 だけを無限に増やしても約 47.4 µs が限度です(本数の曲線から外挿)。
- **期待**: −1.5〜2.3 µs。
- **確かめ方(選び方の甘さを除く)**:
  - 新しい種 2 で v0 と多段型を 1 本ずつ学習します。約 22 + 34 分です。
  - 規則を先に固定して、組(v0_s2 + 多段型_s2)を A と比べます。今ある 2 組と合わせて判定します。
  - 走行では 2 つのエンジンを順に呼びます。run_numpy は 2.37 + 3.19 = 5.6 ms で、ゲート 6 ms の内ですがぎりぎりです。実機の走行ループで時間を測ります(drive.py に 2 本の平均を足す変更が要ります)。
- **危険**:
  - 推論の時間・GPU のメモリ(エンジン 2 つ)。
  - 効果は開いたループの指標で、閉じたループ(実車)での効果は未確認です。A/B/A のカードが要ります。
  - 1 本に戻したい場合は、アンサンブルの出力を先生にした蒸留を考えます。ただし、先生は学習のフレームを覚えています(学習の誤差 14 µs)。先生の出力が人の値とほぼ同じになるので、交差で作った先生が要り、GPU が数倍かかります。

### ② 駆動の効き(バッテリー)を入力に入れる
- **証拠**: 2.2 節。パラメータなしの直し(1500 − thr' = (1500 − thr) × 効きの比)だけで、A 種 0 は 49.15 → 47.39 µs、種 1 は 49.46 → 47.79 µs、B は 49.14 → 47.37 µs になりました。問題のシーンは 96.7 → 71.3 µs、ほかのシーンは 42.5 → 44.1 µs(悪化)です。
- **案**:
  - 直前 5 秒の「速さの中央値 ÷ (1500 − 実際に出したスロットル)の中央値」を、ゆっくり変わるスカラーの入力として足します。
  - 学習では人の操作から、走行では AI 自身の出力から計算します。
  - 別の案として、目標の速さを出力し、eRPM の帰還でスロットルを決める方法もあります(TCP の制御器の形)。
- **期待**: 主指標で −1〜3 µs です。ほとんどは問題のシーンの分です。実車では、バッテリーが減っても遅くならない効果が期待できます。
- **確かめ方**:
  - 先に CPU で、効きの比を特徴にした補正を、シーンを 1 つずつ外した交差で当てはめます。ほかのシーンを悪くしない形か(縮める・ジャンル別にする)を確かめます。
  - そのあと v0 の入力を 1 つ足して、種 0・1 で各約 22 分学習します。主指標と、「193638-0003 を除いた L1」の両方で判定します。
- **危険**:
  - 過去のスロットルの集計を入れるので、弱い copycat になりえます(5 秒の中央値なので小さいと見ています)。
  - 証拠は val の 1 シーンに頼っていて、学習側にも同じ変化(150424 の 0004・0005 など)があるかで効き目が変わります。
  - 電圧が記録されていないので、原因は推定です。

### ③ 間引きで捨てている 2/3 のフレームを使う(位相をエポックごとに変える)
- **証拠**:
  - `--stride 3` は「番号が 3 の倍数のフレームだけ」(`jetformer/train_data.py` 148 行)で、位相が固定です。
  - 実機の学習の 27,502 フレームのうち、使っているのは 5,912 だけです。IMU の 3 つの位相の 1 つしか見ていません(シミュレーターで見た問題)。
  - 学習 14 µs vs 検証 49 µs の開き、種を足すと約 1〜2 µs 下がること(ばらつきの成分)から、データの多様さを増やす余地があります。
- **案**: 学習のときだけ、エポックごとに位相 0・1・2 を回します(または stride 1 で 10 エポック)。勾配のステップの数は今と同じです。検証(best の選び方)は今のままにします。
- **期待**: −0.5〜1.5 µs(不確か)。隣のフレームとよく似ているので、小さいかもしれません。
- **確かめ方**: 腕 ALL を種 0・1 で、各約 22 分学習します。固定した規則で A と比べます。
- **危険**: 小さい変更なので、壊れる危険は低いです。効かない可能性はあります。

### ④ 実機のデータ量と誤差の学習曲線(測定)
- **ねらい**: 底の中心は約 31 µs で、余地があります。その余地を「実機の録画を増やす」ことで取れるかを見ます。シミュレーターは画像の差で効きませんでした(10/13・10/15)。
- **やり方**: 学習の 41 シーンのうち 1/4・1/2 を選んで学習します(ログ単位で、ジャンルの割合をそろえる)。種 0・1 です。誤差 = 底 + b·N^−α を当てはめ、全部のデータの 2 倍で何 µs 下がるかを出します。
- **GPU**: 1 本 約 6〜12 分、4 本で約 40 分。
- **使い道**: 2 倍で 3 µs 以上下がる見込みなら、ユーザーにきれいな周回の録画(高速・低速、バッテリーの残りも記録)をお願いする根拠にします。平らなら、データより形(①)に投資します。

### ⑤ 時間のアンサンブル(試し済み・不採用)

| | 元 | 時間のアンサンブル(重み exp(−1·j)) |
|---|---|---|
| best(A 種 0 / 種 1) | 49.146 / 49.457 | 48.352 / 48.701(−0.78) |
| last(A 種 0 / 種 1) | 49.235 / 49.752 | 48.469 / 48.981(−0.77、閾値 1.322 未満) |
| 判定 | — | **同等**(best だけ「良い」→ 規則で下げる) |
| 介入の集合 | 128.9 / 127.8 | **129.9 / 129.3(悪化)** |

- 推論は増えませんが、介入で悪くなるので反応が遅れる向きです。重みも後から選んだものです。**実車では試しません。**
