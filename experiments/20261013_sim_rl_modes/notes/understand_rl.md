## 0. 要点(モードを作る人へ)

1. **環境**は `rl/env_core.mjs` の `RlEnv`(1 環境)。`reset({gate, left_offset_m, left_yaw_deg, seed, perturb})` → 停止状態から開始、`step(a0, a1)` → 報酬・終了。
   物理はユーザーの `sim-core.js` そのもの(高速版は元とビット単位で同じ)。Python からは `NodeVecEnv`(4 ワーカー × 16 環境)。
2. **観測(79 次元)**は「参照ループ R(教師の線、26.12 m)への射影 + 先読み 16 点(0.25〜4 m)」「19 本のレイ(10° おき、3 m、高さに関係なく全障害物)」
   「車体と全障害物の最小距離 d_min」「今の目標ゲートの along/lateral」「速さ・舵角・ヨーレート・前回の行動・路面 μ」。
   壁・柱は **レイと d_min で見えている**。参照線・先読みは障害物を知らない。**R と 33 ゲートは v3 コース専用**(ほかのコースの経路では例外)。
3. **今のベストラップの方策は「1 本の線」しか走らない。** 今日の 60 シーンの物差し(同じ時刻の舵 PWM の、シーンの平均からの差)を Node で作り直すと、
   教師 60 条件は **7.58 µs**(ユーザーへの報告の 7.6 µs と同じ)。RL の方策で同じ 60 条件は 40 µs だが、線の違い(横ずれ e_y)は 1.0 cm だけで、
   差の多くは RL の舵の荒さ(ぎざぎざ)によるものと見られる。広い開始から走らせても 3 m 走ると同じ線(1.9 cm)に戻る。**「いろいろな経路」は学習で作る必要がある。**
4. **学習し直さずにできるばらつき**: (a) 開始をアプリの入力の範囲いっぱい(ゲート 0〜32・±0.3 m・±25°)に広げる → 障害物と重ならない 782 開始のうち **93%** が 20 秒をぶつからず・ゲートを逃さずに走る。
   (b) 速さの上限を掛ける → 4.5〜2.0 m/s で完走(1 周目 8.09 → 13.8 秒)、1.5 m/s では衝突。ただし 2.5 m/s 以下ではすき間が 1〜4 cm に減る。
   (c) ベストラップの作業のチェックポイント 7 つ(種・ステップ違い・r2)を混ぜる → 線の違い 4.9 cm、舵 56 µs。
   (d) 舵に小さな白色雑音(σ 0.05 rad)を足す → 12/12 で完走(DART 風。雑音は状態と無関係なのでラベルの平均は方策の操作のまま)。
5. **学習し直しが要るもの**: 線のずらし(観測の R を ±5 cm より大きくずらして見せると衝突)、障害物の回避(R の上の柱 6 か所のうち 4 か所で衝突)、
   立て直し(舵を端に 0.2 秒固定する乱れで 50%、0.4 秒で 30% しか生き残らない)、物理のずれへの強さ(r1: 舵の速さ 1.0 rad/s で衝突)。
6. **状態の乱し**(向き・横の瞬間的なずれ)は **Node の高速版でだけ**できる(`sim.peek().state` を書き換える。何もしない書き換えで結果がビット単位で同じことを確認)。
   **ブラウザの記録では状態に触れない**(教師の差し込み口は snapshot の写ししか受け取らない)ので、記録の乱れは **行動の差し込み**(舵のパルス・雑音)だけ。
   さらにアプリの集約は「瞬間移動・衝突・動的な初期状態・600 フレーム未満」のシーンを拒否する。乱れのフレームのラベルを外すには、
   行動の `info` に印を付けて(フレームの台帳 `simulation/frames.jsonl` に入る)、JetFormer の取り込みで `future_valid` を落とす処理が要る。
7. **障害物の追加**は「sim を作る前の world の `disks`/`segments` に足す」なら、衝突(高速版・元とも)・方策のレイと d_min・`sim.observe()` のすべてに効く。
   **作ったあとに足すのは効かない**(高速版は近傍の表を作るときに固定する)ので、回(エピソード)ごとに配置を変える。
   注意: (1) 10° おきのレイは細い柱を見逃す(正面から 6° ずれた 1.35 m 先の直径 10 cm の柱はどのレイにも当たらない)、
   (2) `prepareGeometry` のキャッシュは消えない(配置を毎回変えると 1 回 約 14 KB ずつ増える)、
   (3) ブラウザではコースは読み込み時に 1 回だけ作られ、カメラ・ToF に映すには 3D の物体も要る(コースの差し替え = JetFormer の scene.js の配信で可能)。
8. **すき間の上限**: R に沿って車体を横にずらして測ると、一番狭いのは奥の直線(ゲート 21〜25、x −0.4〜−2.5, z −2.45)で、そこで取れるすき間は最大 **14 cm**
   (5 cm のすき間で動ける横の幅は 0.18〜0.36 m)。ほかの区間は 5 cm のすき間で 0.5〜1.9 m の幅がある(黒シートの近道は R の右がほぼ 0)。「絶対壁にぶつからない」の目標は 8〜10 cm が現実的。
9. **PPO の速さ**: 64 環境で 5,300〜5,800 steps/s(収集 1.1 秒 + 更新 1.7 秒 / 16,384 ステップ。更新のほうが長い)。1,000 万ステップ 約 30 分、
   今の方策から 500 万ステップの続き 約 15 分。メモリは学習側 約 0.65 GB + ワーカー 4 × 130 MB(`--mem 2G` に収まる)。Firefox の記録と重なると約半分。
10. **ベストラップの作業の今**: 検証済みの最良は `main` 種 1 の 1,000 万ステップ(`rl/best/main/policy.json`、sha256 `7c43cb53…53ee`、停止から 8.092 秒・
    フライング 7.656 秒、確認 r1 で本物と判定)。r2(物理のランダム化で 500 万ステップの続き)は 21:29 に学習が終わり、いま頑健さの評価中(その作業のプロセス)。
    記録の段(ブラウザの差し込みモジュール `rl-teacher-bestlap.js`)はまだ作られていない(自己テスト版 `web/rl-teacher-selftest.js` だけ)。

## 1. 環境の API

### 1.1 `RlEnv`(`rl/env_core.mjs`、Node)

| 呼び方 | 中身 |
|---|---|
| `new RlEnv({core, coreKind, baseWorld, variant, mode, episodeMode, timeLimit, teacherModule, teacherActions, reward})` | `core` は `await loadCore('fast'|'original')`。`baseWorld` は v3 の world(`sim/world-v3.json`、sha256 確認つき)。`variant` は `main`(速さの上限 4.5 m/s)か `open`(7.24)。`mode` は `train`(RL の終了つき)か `eval`(sim の終了だけ = アプリと同じ)。`episodeMode` は `continuous`(連続周回 20 秒)か `single`(単周)。構築のときに `this.geometry = prepareGeometry(baseWorld)` |
| `reset({gate, left_offset_m, left_yaw_deg, seed, scenario, noiseStd, perturb})` → `true/false` | アプリの reset と同じ開始(経路をゲート `gate` で回し、左へ `left_offset_m`[±0.3 で切る]、向き `+left_yaw_deg`[±25° で切る])。速さ 0・舵 0 から。障害物と重なると `false`(`invalid_spawn`、呼ぶ側が引き直す)。`perturb = {physics: {steerRate, brakeDeceleration, driveTau, driveAccelerationCap, frictionMultiplier}, delay: 0|1, steerGain, speedGain}`(r2 で足された。観測の μ は標準の物理の値で作る) |
| `step(a0, a1)` → `{reward, terminated, truncated, reason, progress, smooth, traction, clearance, terminal_reward, rho, s}` | 行動を [−1, 1] に切って 1 フレーム(1/30 秒)。`env.obs`(Float64Array 79)・`env.aux`(d_min・横ずれ・ゲートの along/lateral・s など生の値)・`env.view`(高速版は `sim.peek()` の参照)が更新される |
| `stepCommand(steering, speed, a0n, a1n)` | アプリの単位(rad・m/s)で進める(教師・保存した操作の再生用) |
| `summary()` / `report()` | 回の要約(周回時間・終わった理由・最小すき間・報酬の内訳・`gate_miss_frame`)/ sim のレポート(操作列・軌跡。確認器 `verify_lap.mjs` が読む) |
| `resetRandom(env, rng, dist, maxTries, extra)` | 開始の分布(5 章)から引いて reset(重なれば引き直し) |
| `sampleDr(rng, DR_SPECS.r2)` | r2 の物理のずれを 1 回分引く |

- **終了**(`mode: 'train'`): sim の衝突・黒シート違反・周の距離不足(−10)、ゲート逃し(今の目標ゲートの線を越えた = along ≥ 0、−10)、停止(1 秒以降に 0.2 m/s 未満が 60 フレーム、−10)、
  逆走(s が最大値から 1 m 戻る、−10)。打ち切り(罰なし): 20 秒(`collection_duration_complete`)・単周の時間切れ。単周の完走(`route_complete`)は罰なしの終了。
  `mode: 'eval'` は sim の終了だけ(ゲート逃しでは止まらず、最初のフレームを `gate_miss_frame` に残す)。
- **sim はゲートを外すと二度と数えない**(`route_index` が止まる)。連続周回ではその後の周が全部無効になり、観測の「目標ゲート」(77〜78 番)も外したゲートのまま残る
  (r1: 方策は戻ろうとして内側の手すりにぶつかる)。立て直しのモードではここの扱いが要る(8 章)。

### 1.2 ワーカーと Python(`rl/env_worker.mjs`・`rl/vec_env.py`)

- `NodeVecEnv(n_workers=4, envs_per_worker=16, seed, variant, mode='train', dr=None, teacher_actions=False)`。`reset()` → (64, 79) float32、
  `step(a)` → `obs, rew, terminated, truncated, info`(`info['final_obs']` = 終わった環境の終了前の観測、`info['episodes']` = 要約)。自動リセットはワーカー側。
- 命令は標準入出力のバイナリ('I' 初期化 JSON・'R' リセット・'S' 行動 E×2・'Q')。初期化の `starts` は `'random'` か開始の配列(評価用)。
- 乱数は環境ごとに `mix32(種, 通し番号)` の splitmix32。ワーカーの分け方によらず同じ結果。
- **79 は Python 側にも直に書いてある**(`vec_env.py` と `ppo.py` の `OBS_DIM = 79`、書き出しの schema `rl-bestlap-policy/v1` の `obs_dim`)。
  観測を足すなら、写した側でこの定数を引数にする。`policy_forward.mjs`(JS の方策)は重みの `obs_dim` に従うので、そのまま使える。

### 1.3 物理のコア(`sim/fast-sim-core.mjs` と ユーザーの `sim-core.js`)

- `createSimulation(world, config)` → `{reset, step, observe, snapshot, report, demoAction, setPaused}`。高速版はさらに `peek()`(state・metrics・config を参照で返す)・
  `step(action, true)`(写しを返さない)・`world`・`targets` を出す。高速版の置き換えは 3 か所(近傍の障害物だけ判定・写しの省略・peek)で、結果は元とビット単位で同じ(REC60 の全周で差 0)。
- `reset({seed, scenario, initialState})`: `initialState = {x, z, yaw, speed, steering, routeIndex}` で **速さ・舵角つきの途中の状態から始められる**(「動的な回復」)。
  ただし **単周モードだけ**(連続周回では例外 `Continuous laps cannot restore a dynamic recovery state`)。全目標ゲートを通ると `recovery_segment_complete` で終わる(完走には数えない)。
  確認: `probe/recovery_api.mjs` → `probe/recovery_api.json`(ベストラップの走りの 5 秒目、速さ 3.78 m/s の状態から開始できた)。
- `observe()`: sim 自身のレイ(13 本、高さ 8 cm 以上の障害物だけ、雑音つき)。RL は使っていない。
- 1 フレームを小区間(maxSpeed 7.24 なら 31 個、約 1.1 ms)に分けて積分し、各小区間で衝突・ゲート・黒シートを判定する。

## 2. 観測(`rl/features.mjs`、79 次元、Node とブラウザで同じファイル)

| 番号(0 始まり) | 中身 | 割る値 |
|---|---|---|
| 0–2 | 速さ v、実際の舵角 δ、ヨーレート ω = clamp(v·tanδ/0.26, ±μg/|v|) | 4.5・0.52・4 |
| 3–4 | 前回の行動 a0, a1(適用した値) | 1 |
| 5–7 | **参照ループ R** からの横ずれ e_y(左が正)・向きのずれの sin・cos | 0.5・1・1 |
| 8–39 | **R 上の先読み** Δs = 0.25, 0.5, …, 4.0 m の 16 点(車の座標系の 前・左) | 4 |
| 40–55 | その 16 点の路面 μ | 0.8 |
| 56–74 | **19 本のレイ**(−90°〜+90°、10° おき、最大 3 m)。線分(半径つき)・柱(円)・柱の脚(軸に平行な 16×15 cm の四角)・外枠に、**高さに関係なく**当てる | 3 |
| 75 | 車体の中心の路面 μ | 0.8 |
| 76–77 | 今の目標ゲート(sim の `route_index`)の線に対する along(手前が負)・lateral | 2・0.65 |
| 78 | **d_min** = 車体の長方形と全障害物の最小距離(0.5 m で頭打ち) | 0.5 |

- **参照ループ R**: RC 教師の単周の参照(1,091 点)を前後 1.5 m の 3 次エルミートで閉じたもの(`reference_loop.mjs`、sha256 `0bd89546…f97e4`)。
  **座標の物差しと先読みの形にだけ使い、R に沿うことへの報酬はない**(方策は R から 0.3 m 程度離れて走る。e_y の 5%〜95% 点は −0.32〜+0.26 m)。
- **進み s**: 前のフレームの s の −0.5〜+1.5 m だけを探す射影(周をまたいで増え続ける)。リセットのときは目標ゲートの前後だけを探す。
  横に大きく(0.5 m 程度より)跳ぶような状態の乱しをすると、射影が近くの別の場所へ飛ぶおそれがある(0.2 m の横ずらしでは問題なし、8 章)。
- **v3 専用**: `routeOffset(route)` は経路が標準の 33 ゲートを回したものでないと例外。R・ゲートの s(`GATE_S`)も v3 のもの。
  JetFormer にアップロードしたほかのコースでは使えない(使うならコースごとに参照線を作る必要がある)。障害物を足すだけなら経路は同じなので使える。
- **障害物は world から読む**: `prepareGeometry(world)` が `segments`(高さ > 0)・`disks`(`post-foot` は四角、それ以外は円)・`bounds` から作る。足した障害物はレイと d_min に入る。
  ただし `env_core` の `RlEnv` は構築のときの `baseWorld` の形を使う(`this.geometry`)。配置を回ごとに変えるなら、`env.baseWorld` と `env.geometry` を差し替えてから reset する。
  **`prepareGeometry` のキャッシュ(Map、キーは world の JSON 約 14 KB)は消えない** ので、配置を毎回変えるとメモリが増え続ける(写した側で上限つきにするか、キャッシュを通さない)。
- ブラウザでの使い方: `createFeatureTracker(world, config)` → フレーム 0 で `resetProgress(x, z, route_index)` → 毎フレーム `advanceProgress(x, z)` → `observe(state, route_index, 前回の a0, a1, out, aux)`。
  同じフレームで 2 回呼ばれても 2 回進めないようにフレーム番号で覚えるのは差し込みモジュールの仕事。

## 3. 行動の単位

- 方策の出力 a ∈ [−1, 1]²(展開時は平均)。**舵の指令 = 0.52·a0 [rad](正が左)、目標速度 = V_cap·(a1+1)/2 [m/s]**(`main` は V_cap 4.5、`open` 7.24)。後退なし。
  `actionToCommand(a0, a1, speedCap, maxSteer)` / `commandToAction(...)`。
- アプリの収集器のラベル(PWM): 舵 = 1442 + a0·558(a0 ≥ 0)/ 1442 + a0·442(a0 < 0) µs、スロットル = 1498 − (v_cmd/7.24)·498 µs(4.5 m/s で 1188.5 µs)。
  正解ラベルは「適用した PWM の 1〜10 フレーム先」。アプリは **実際に適用した指令** の PWM を保存する(行動の `info` の PWM が違えば使わない)。
- 選んだ方策は舵の指令が端にいる時間 20%、速さの指令は 4.5 と 0(= 一定 1.2 m/s² のブレーキ)の 2 値が約 7 割(「教師より荒い」)。

## 4. 報酬(`rl-bestlap-reward-v2-gatecap`、1 フレームごと)

```
r = clip(min(s, 目標ゲートの s + 0.75) の増分, −0.3, v·dt + 0.05)   進み [m](射影の飛び・ゲートの手前の空き地への抜け道を防ぐ頭打ちつき)
  − 0.02·(Δa0)² − 0.01·(Δa1)²                                        なめらかさ
  − 0.02·max(0, ρ − 1.1)、ρ = v²|tanδ| / (0.26·μ·g)                  横の頭打ちの超過
  − 0.05·max(0, (0.05 − d_min)/0.05)                                すき間 5 cm 未満
終了の罰 −10: 衝突・ゲート逃し・黒シート違反・周の距離不足・停止・逆走。20 秒の打ち切りは罰なし(価値で補う)
```
- 進みが 1 フレームの最大で、周の賞与は無い(20 秒で進む距離の最大化 = 周回時間の最小化)。
- 学習が進むと速さと引き換えにすき間を削る(種 0 は 1,000 万ステップで 0.2 cm)。すき間の罰は小さい(1 フレーム最大 0.05)。
  「壁にぶつからない」モードでは、すき間を罰ではなく **約束(しきい値で終了、またはラグランジュ乗数)** にするのが rl.md 10 章の第 1 案。

## 5. 回(エピソード)と開始の分布

- 停止から 20 秒(600 フレーム)の連続周回。開始: 半分はゲート 0、半分はゲート 0〜32 から一様。横ずれ U(−0.12, 0.12) m・向き U(−8°, 8°)。
  重なる開始は引き直し(3,000 回で 0 回)。種は環境ごと。
- アプリの入力の範囲はもっと広い(ゲート 0〜32・±0.3 m・±25°)。今の方策でこの範囲の格子(33 ゲート × 5 × 5)を走らせた結果は 9 章。
- 評価の条件(`rl/eval_sets.mjs`): REC60(記録の 60 条件 = ゲート 0・±3 cm・±3°、雑音の 30 条件は RL には効かない)、STD(標準の開始の単周と連続)、
  ROB24(±0.10 m・±6° とほかのゲート)、閉ループの開始 E0〜E5。

## 6. 速さ・舵の限界と RC の応答(物理)、ずらせるつまみ

sim-core の 1 小区間 h(≤ 10 ms)ごとの式(`real-drive-response-estimate-v1`):

| 量 | 式 | 標準の値 |
|---|---|---|
| 加速(目標 > 今) | rate = min(driveAccelerationCap, μ·g, (目標 − v)/driveTau) | cap 6 m/s²、τ 0.40 s |
| 減速(目標 ≤ 今) | **いつも一定** brakeDeceleration | 1.2 m/s² |
| 舵 | 舵角が指令へ steerRate·h ずつ近づく(サーボの速さ) | 1.2 rad/s、最大 0.52 rad |
| ヨーレート | v·tanδ/0.26 を ±μg/|v| で頭打ち(滑りはなく、頭打ちのあいだも速さは落ちない) | 路面 μ: カーペット 0.8・黒シート 0.7・青マット 0.65・芝 0.6・PTFE 0.22 |
| 位置 | 中点の向きで積分 | — |

- **摩擦円はない**: 縦(加減速)と横(ヨーレートの頭打ち)は別々に制限される。r1 は自前の積分で摩擦円(縦を √((μg)² − a_lat²) まで)を入れた反事実を作り、
  RL も教師もぶつかると確かめた(`check_r1/own_physics_r1.mjs` の `frictionCircle` 選択肢)。sim で摩擦円を使うには、高速版と同じ文字列の置き換えで `nextSpeed` の rate を変える必要がある
  (学習だけに使い、記録はユーザーの sim のまま、という形なら「より控えめな走り」を作るつまみになる)。
- **ずらせるつまみ**(sim-core の config がそのまま受け付ける値と範囲): `steerRate` 0.01〜20、`frictionMultiplier` 0.01〜5(全路面の μ に掛かる)、`driveTau` 0.05〜2、
  `driveAccelerationCap` 0.01〜20、`brakeDeceleration` 0.01〜20、`maxSteer` 0.01〜1.2、車体の寸法、`dt` 1/120〜0.1、`noiseStd`(sim のレイだけ)。
  路面ごとの μ は world の `surfaces[].mu` を変えれば変わる(観測の μ も変わる)。
- `env_core` の `perturb`(r2): 上の 5 つ + 制御遅延 1 フレーム + 舵・前進のゲイン。`DR_SPECS.r2` = 舵の速さ 0.85〜1.7・ブレーキ 0.8〜2.0・τ 0.3〜0.5・加速の上限 4〜6・μ ×0.88〜1.08・
  遅延 1 が 5 割・ゲイン ±5% / ±3%、回の 2 割は標準。**観測は標準の物理の値で作る**(方策は今の物理を知らない)。
- 制御遅延: アプリの遅延(`control-delay.js`)は「外部の AI の評価専用」で、教師の差し込み口(記録)は遅延 0。RL の学習・記録も遅延 0 が約束。
- アプリの「評価条件」: `low-friction` は μ × 0.4(RC 教師の約束では拒否)、`dim` は照明だけ(物理は同じ)、`noise` は ToF に 25 mm の雑音(物理は同じ)。
- r1 の物理のずれへの強さ(選んだ方策): 遅延 1・μ ×0.9〜1.05・時定数 0.3〜0.5・ブレーキ 1.1〜2.0 は完走、**舵の速さ 0.9〜1.0 rad/s で衝突**、ブレーキ ≤ 1.0 や舵の速さ 1.5 で連続の 2 周目に衝突。

## 7. すき間(壁・柱との距離)の計算

- 観測・報酬の d_min(`features.clearance`): 車体の長方形(0.42 × 0.19 m)を車の座標系に置き、線分は「線分と長方形の距離 − 半径」、柱は「点と長方形の距離 − 半径」、
  柱の脚は「四角の 4 辺と長方形の距離」、外枠は「車体の 4 隅から枠まで」。当たっていれば 0、遠ければ 0.5 で頭打ち。フレームの終わりの姿勢で 1 回。
- 確認器(`rl/lap_audit.mjs`・`check_r1/own_physics_r1.mjs`): 車体の多角形と障害物の正確な距離(辺どうしの線分の距離 + 内側の判定)を **小区間ごと** に、近いときは小区間の間も補間して測る。
  REC60 の最小すき間 5.69 cm(柱の脚)は両方で同じ値。
- **コースの幅**(`probe/corridor.mjs` → `probe/corridor.json`): R の上 5 cm ごとに、車体を R の接線の向きにして横へ 1 cm ずつずらし、すき間 c 以上で動ける横の範囲を測った。

| 区間(ゲート) | すき間 5 cm で動ける幅(最小 / 中央値) | R から左・右へ動ける最小 |
|---|---|---|
| 0→3(最初の直線) | 0.83〜0.94 / 0.92〜1.03 m | 左 0.34・右 0.24 m |
| 3→8(U ターン) | 0.86〜1.52 / 0.90〜1.55 | 右 0.14 |
| 8→12(黒シートの近道) | 0.53〜0.96 / 0.61〜0.97 | **R の右はほぼ 0**(R が内側の柱に 4 cm まで寄る)、左 0.5 |
| 15→18(芝・PTFE) | 1.24〜1.84 / 1.42〜1.88 | 広い |
| **21→25(奥の直線)** | **0.18〜0.32 / 0.29〜1.06** | **左右 0.08〜0.13 m** |
| 25→33(青マット〜ゴール) | 0.94〜1.39 / 1.01〜1.39 | 左 0.26 |

  - 各 s で横にずらして取れる最大のすき間の最小(コースで一番きついところ)は **14 cm**(s ≈ 17.9〜18.1、x −2.3, z −2.45、ゲート 24〜25 のあいだ)。
    5% 点は 20 cm。**「絶対壁にぶつからない」で全周 10 cm 以上を求めると、奥の直線では中心から ±2 cm 程度しか許されない**。8 cm 程度が現実的な目標。
  - 線をずらすモードの幅も、区間ごとに大きく違う(ほとんどの区間で ±0.3〜0.5 m、奥の直線では ±0.1 m)。区間の幅に比例させてずらす形が要る。

## 8. 状態の乱し・行動の差し込み(「離脱復活」の作り方)

### 8.1 どこで何ができるか

| 方法 | Node の学習(高速版) | Node(元のコア) | ブラウザの記録(アプリの教師の差し込み口) |
|---|---|---|---|
| 行動の差し込み(舵のパルス・雑音・速さの指令) | ○(`step` の前に行動を変える) | ○ | ○(差し込みモジュールの `action()` が返す値。**ラベルにもそのまま入る**) |
| 状態の乱し(向き・位置・速さを瞬間的に変える) | ○(`sim.peek().state` の x・z・yaw・speed・steering を書き換える。次の小区間で `{...state}` として引き継がれる) | ×(snapshot は写し) | ×(`action(sim.snapshot())` は写し。アプリの `sim` はモジュールの中の変数で外から見えない) |
| 速さ・舵角つきの途中の状態から始める | ○(単周の `initialState`) | ○(単周だけ) | 単周の「動的な回復」だけ(`controller: demo`・出典 `initial-state-provenance` が要る・連続の集約には入らない) |
| 障害物の配置を変える | ○(sim を作り直す = 回の始め) | ○ | コースの読み込み時だけ(9 章) |

- 何もしない書き換え(フレーム 150 で `yaw += 0`)で周回時間がビット単位で同じことを確かめた(`kicks.json` の `C_noop_identical: true`)。
- 状態を書き換えると、保存した操作列の再生(確認器)とは合わなくなる(乱しは操作列に残らない)。学習には問題ないが、記録の確認には使えない。

### 8.2 アプリの記録と集約が求めること(`dataset_recorder.py`・`qa/combine_scene_datasets.py`)

- 教師の差し込み口(`createRcTrainingTeacher(world, config, variation)` → `{action, reference: {length, planned_time_s}, options, metadata}`、`assertRcTeacherContract`、`RC_COLLECTION_PLAN`)。
  `action(snapshot)` の戻り値 `{steering, speed, info}` の `info` は **フレームの台帳 `simulation/frames.jsonl` の `action_info`** にそのまま入る(1 フレーム 128 KB まで)。
  ただし `info.steering_pwm` / `info.throttle_pwm` は特別扱い(適用した指令と合わなければ無視)なので使わない。
- 20 分の集約(「60 シーンの収集」、app.js が `/api/datasets/collection` を `require_collision_free: true` で呼ぶ)が拒否するもの:
  600 フレームでない・30 Hz が途切れる・**衝突がある**・**フレームの間で姿勢が飛ぶ**(前のフレームの終わりの姿勢と次の始まりが 1e-7 を超えて違う)・
  `initialState` の回・連続周回でない回。さらに **全シーンで同じでなければならない**: `context.teacher`(= 差し込みの `metadata`)・物理(`physics_signature`)・センサー・world_version・経路・ジャンル。
  → 物理のずれ・センサーの違いで記録するなら、条件ごとに別の集約(または 1 シーンずつの ZIP。JetFormer はどちらも取り込める)。モードの ID は `metadata` に入れてよいが、
  シーンごとに変わる値(開始・乱れの時刻など)は `metadata` に入れない(`info` か、`config.seed` から決める)。
- 連続試験の計画(`batch-plan`)の 1 条件に書けるキーは決まっている(フォームの項目・`name`・`dataset-mode`・`dataset-split`・`initial-state` など)。
  「RL のモード」を条件に書く欄は無い。差し込みモジュールが受け取るのは world・config(**シーンごとの `seed` を含む**)・開始の variation だけなので、
  モードは画面の選択(JetFormer 側で URL や localStorage)で決め、シーンごとのばらつきは `config.seed` から決定的に作るのが素直。
- 乱れのフレームのラベルを外すには: アプリの収集器は「自動のラベルは全部有効」(`vehicle_valid` はセッション単位)なので、JetFormer 側で台帳の `action_info` を読み、
  乱れのフレームとその 10 フレーム前までの `future_valid` を偽にする処理を足す(JetFormer の `train_data.py` は `future_valid & vehicle_valid` のフレームだけ学習に使う)。
  集約の検査は `future_valid` が「最後の 10 フレームだけ偽」であることを求めるので、**書き換えは集約・取り込みのあと**(JetFormer の中)で行う。
- 小さな **白色** の雑音(状態と無関係)は、ラベルを外さなくても平均で打ち消される(DART 風)。相関のある雑音(OU)は状態と相関するので偏る。

### 10.2 条件付きの方策に要るもの

- **features.mjs は変えない**(79 次元はブラウザと Node で共有)。写した側に薄い包み(例 `features_modes.mjs`)を作り、`observe()` の 79 の後ろに条件を足す:
  目標の速さの上限 c_v = V_cap/4.5、線のずらし c_o(−1〜1)、すき間の目標、モードの番号(one-hot)など。ブラウザの差し込みモジュールも同じ包みを使う。
- 線のずらしは、区間の幅が大きく違う(7 章)ので「目標の横ずれ = c_o × その s での片側の空き幅」の形にし、空き幅の表(`corridor.json` と同じ作り方、5 cm おき)を
  Node とブラウザで共有する。報酬に「目標の線からの外れ」の項を足す(進み・すき間の項はそのまま)。先読みの 16 点を「目標の線」の点に置き換える案もある。
- 速さは回ごとに V_cap を引き、`actionToCommand(a0, a1, V_cap)` で行動の意味を変えるか、行動は 4.5 のままで上限を観測と報酬で教える。
- Python 側(`vec_env.py`・`ppo.py`・書き出し)の `OBS_DIM = 79` を引数にする。今の方策から始めるなら、1 層目の重みを新しい入力の分だけ 0 で広げる(初めは今と同じ走り)。
  観測の正規化(移動平均)は新しい入力の分を 0 平均・1 分散から始める。
- 1 つの条件付きの方策にするか、モードごとに別の方策(別の PPO)にするかは選べる。別の方策なら観測・コードはほぼ今のまま、報酬と開始・乱れだけ変えればよい
  (今の方策から 500 万ステップ続けて約 15 分 / 本)。

## 13. モードの設計への示唆(この段の判断。次の段で決める材料)

| モード | 今すぐできること | 学習で足すこと | 記録で気をつけること |
